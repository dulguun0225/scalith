# Build a feature — evidence

For a human deciding whether to trust the directive text. Every claim below is *convention* — a decision recorded with its date and observed ground, no research pass and no refutation panel behind it.

## Run the workflow; orchestrate nothing yourself

The run this skill is modelled on, 2026-09-16 to 2026-09-17: `specify workflow run speckit` driven from inside a Claude Code session for the `002-product` feature of a Java backend, with the session answering both gates after spawning a fresh-context Opus review of each artifact. Both reviews found blocking defects the writing context had passed — the constitution lagging the plan, a test-property precedence error, an ArchUnit scope error — and each was fixed in the artifact and committed before the gate was approved. Timings from the engine's own log: specify 19 minutes, plan 29, tasks 11, implement 53; the tasks step exited 1 on a transient spend-limit error after writing a complete `tasks.md`, and the run was resumed by patching the engine's state file. A later `/speckit-converge` appended eight gate and documentation gaps as a ninth phase, all implemented; the second converge is expected to report converged.

What spec-kit's engine (specify-cli 1.0.7) can and cannot do, read from its source the same day: a `command` step carries `model`, passed as `--model` to `claude -p "/speckit-<stem> <args>"`; per-step `integration_args` and `integration_options` exist in the schema but the Claude integration inherits the base `validate_runtime_config`, which raises on any value, so `--effort` can only reach the child through `SPECKIT_INTEGRATION_CLAUDE_EXTRA_ARGS`, one value for every step of the run. A `gate` step returns `PAUSED` when stdin is not a TTY. A `command` step's stdout is not captured ("a planned enhancement" in its docstring), so a `while` step cannot be conditioned on what converge reported. A `shell` step could run `claude -p` with any flags, but then the engine contributes nothing the script here does not.

Alternatives weighed and rejected, 2026-09-17: a Node script driving `claude -p --model --effort` per stage from a terminal — the same control flow, re-implementing the resume, journal and progress that the Workflow tool already has, and needing its own permission and environment handling for the child sessions; and one orchestrating agent that invokes the speckit skills in its own context — the human gate moved into the writer's context, which is the failure the two fresh reviews caught.

## The spec is fixed input, and no stage of this run edits it

Ground: the owner's decision of 2026-09-21, settled before the change was written. The team's workflow moved — a domain expert writes `specs/<NNN>-<name>/spec.md` inside the service project with stock `/speckit-specify` and `/speckit-clarify`, so the feature branch, the feature directory and `.specify/feature.json` exist before any unattended run starts, and the build begins at `/speckit-plan`. At the same time the service repos dropped the upstream-provenance layer of their traceability gate, so the documents the specify prompt used to pin, account for and cite are gone from those repos and from every prompt here. **Nothing was executed: no Workflow run has started from this shape.**

Two things follow, and the second is the one worth arguing. The first is arithmetic: the specify, clarify and spec-review stages, their fix agents, their tier rows, their round counter, their schemas and the two arguments that named the source document and the spec-kit short name are deleted rather than made optional, because a stage nobody enters is a second way to build a feature that no gate exercises. The second is that the spec becomes an input the run may read and not write. The alternative — let the fix agents keep editing it, since they are the same agents as before — was rejected on what the artifact is for: `spec.md` is now the only artifact in the run that no agent of the run authored, and that is the whole of its value as the oracle every later gate is judged against. An artifact the run may rewrite cannot refute the run. The cost is a new class of stop: a finding whose only remedy is a spec change ends the run instead of being absorbed, which is why the two fix rows carry `specChanges` and why the implement prompt admits a third blocker. That is the honest trade, not a gap — the run can close a gap in the plan, the tasks, the code and the gates, and a gap in the spec belongs to the person who wrote it.

The review that used to refute the spec against its source document is gone with the source, and the gate that remains has to keep an outside oracle: review-plan refutes `plan.md` against `spec.md`, the constitution and the code, none of which that stage wrote. Where a requirement makes every plan wrong, the reviewer is told to say so as a spec change rather than to propose a plan that contradicts the spec quietly.

## A gate is a fresh-context refutation, not a human

Ground: the two gate reviews of 2026-09-16 above, each a fresh Opus context prompted to review, each finding blocking defects. The refutation framing and the findings-as-data return follow the Workflow tool's adversarial-verify pattern, where a verifier prompted to refute catches plausible-but-wrong artifacts that a verifier prompted to approve waves through. The round caps are a decision: two fix rounds for a spec or plan, because a third round on the same findings means the finding is contested and a person should read it; three converge rounds, because the one observed converge appended eight tasks and a second is expected to append none — a prediction refuted and the cap raised to six on 2026-09-18, recorded at the foot of this file.

## Analyze goes back to the artifact it names; converge goes back to implement

`/speckit-analyze` is read-only by its own text and ends by offering remediation edits to the user; `/speckit-converge` is append-only by its own text and reports `converged` or `tasks_appended`. Both give the loop a clean signal. Editing in place rather than re-running was decided on 2026-09-17 from the review-fix commits of the `002-product` run: each `/speckit-*` command regenerates its file whole, so a re-run would have discarded those fixes.

## Unattended means the agent decides by a written rule

The interactive points in the installed skills, read 2026-09-17: `/speckit-specify` presents up to three clarification questions and waits; `/speckit-clarify` is a one-question-at-a-time loop of up to five; `/speckit-implement` stops on an unchecked checklist and asks; `/speckit-analyze` asks whether to suggest remediation. Each had a rule in its stage prompt, and each rule wrote its decision into the artifact so the next review could refute it. The first two are no longer this script's to answer (2026-09-21): a person runs them before the run starts, and an unresolved `[NEEDS CLARIFICATION]` marker left in the spec is preflight's refusal rather than a question an agent answers for its author.

## What this skill does not do

The skill is inception-cadence for a feature — it fires once per feature, and its frontmatter is paid every session; it exists because the alternative was a person at two gates and a night of attention per feature. The sequential shape is a decision: spec, plan, tasks and code are one dependency chain, and the one place work could fan out — implement phases — is kept sequential because each phase's wall run touches the same tree.

**2026-09-18, the converge loop can author its own repair; a `converged`-with-findings round no longer stops it.** Ground: run `wf_7e4e8726-4b5`'s successor handoff on feature `specs/002-product` of the product-catalog repo. The defect was structural, not a mis-set threshold. The loop had exactly two moves: converge appends tasks and implement runs them. It could not author work itself, so the only thing it could do with a finding converge had graded and declined to append was hand it to a person — and the comment beside that branch already admitted the trap: *converge judging a gap non-actionable is exactly the judgment this floor refuses to make on its behalf.* Under the `NONE` default, where every graded finding is above the floor, that branch fires on any finding at all, so the shipped default dead-ended on cosmetics. The coherent reading of the floor is that a run which declines converge's non-actionability judgment owes the work that judgment withheld.

So the loop has a third move. On a `converged` return carrying findings above the floor it dispatches one `force-append` agent (a new `TIERS` row, Opus medium) with those findings rendered by the script and no mention of the floor; the agent appends `## Phase N: Convergence (forced round n)` to `tasks.md` in `/speckit-converge`'s own append format, one task per finding, commits `tasks: forced convergence round n`, and the phase then goes through the same `implementPhase` and the same wall gate as an ordinary appended round. The row is priced with converge and implement rather than with `handoff`, and the difference is the reason: `handoff` is handed a finished document and can only substitute two placeholders, where this agent is handed findings and must author the task text and judge per finding which closure route it leads with.

Four decisions worth their reasons. (1) **A forced task is closable two ways and its own text says both** — fix the defect, or record in `<featureDir>/convergence-rationale.md` why it is not a defect, with the rationale closing the task only once it is in the file. This mirrors what the handoff document already asked a person to do, and it is not a softening: in the `002-product` case FR-034 and FR-035 are requirements about *absences* — this capability contains no approval gate, no user-permission check lives here — and a task demanding a code citation for an absence invites a fabricated one, which is worse than the open finding. (2) **A finding is forced at most once**, keyed on severity, location and summary normalised, tracked across rounds and returned as `converge.forced`; converge has no fixed point (the `001-product-hierarchy` entry above) and each pass perturbs the tree the next one reads, so an unbounded force would spin. The identity is exact-match, so a finding the next round re-words is a new identity — stated rather than hidden, because the bound that actually holds is `maxConvergeRounds` and the identity only decides when the loop may claim it already tried. (3) **A survivor still escalates and says so**: the `needs-human` `why` records that the loop appended a task against this finding and implemented it with the wall green, and the assessment reports it again. A person reading a handoff must know the difference between nobody having tried and the loop having tried and failed. (4) **Round accounting**: the forced round runs inside the slot of the round that discovered it, and the loop then re-assesses exactly as after an appended round, so `maxConvergeRounds` — still 6 — remains the single bound on the stage's cost and a pathological run cannot spin. The extra price of a forced round over an appended one is one `force-append` agent.

The `converged`-with-findings escalation is the rejected alternative, and it is what this skill shipped from `cc903d0` on 2026-09-18 until this change the same day. The ground it lost on is the `002-product` handoff: it asked a person to *decide whether it is real, and either apply the fix or record why it is not a defect* — both of which the run's own agents can do, on findings the script had already filtered. What it got right, and what is kept, is that a finding nothing has closed must not be silently tolerated; the forced round closes it instead of tolerating it or delegating it.
