## Branches

Service projects work trunk-based on the base branch ([SKILL.md](SKILL.md)). What each start does on the base branch and the build branch:

- **Planning runs on the base branch.** A start at `preflight` through `analyze` refuses a dirty tree, checks the base out when it started elsewhere, and brings it up to date from origin by fast-forward only (`git fetch --prune origin && git merge --ff-only origin/<base>`); a failure, or a local base holding commits origin lacks, is a stop. It refuses while the feature's build branch, local or on origin, holds commits the base lacks: the spec is fixed once that branch exists, and the build's ticked tasks are there. A build branch with nothing the base lacks is no build yet. Planning commits only in the feature directory, plus what the plan step writes outside it: the managed section of the agent context file, which spec-kit's opt-in agent-context extension refreshes in its `after_plan` hook, an admitted constitution amendment, and a `docs/GATES.md` entry the plan records. Nothing is pulled between stages; before each push, `git pull --rebase origin <base>` moves only the run's own commits, a push origin refuses because it moved is tried again up to 3 times, and a conflict is `git rebase --abort` and a stop. A run that ends planning pushes its commits.
- **The plan review records the spec it read**: the blob id of `spec.md` at the base's HEAD, one line in `<featureDir>/spec-reviewed.sha`, committed with the plan. Every later start from `tasks` on, the build-branch step and the end-of-planning push compare the base's `spec.md` blob with it; a mismatch or a missing record before the build branch exists is a stop whose restart is `from: "review-plan"`.
- **The build gets a branch that lives only for the build: `build/<NNN>-<name>`**, or `args.branch`. It is looked up by that name only, never by the bare `<NNN>-<name>` spec-kit's `git` extension gives the branch it makes for `/speckit-specify`. A start at `implement` or later brings the base up to date the same way and reads everything it checks from the base's commit, checking nothing out. **Only once every preflight check has passed** does it resume the build branch — local, or on origin, fast-forwarded to origin's where that is ahead — or make it from the base and push it to origin at once, so a preflight stop leaves no branch behind. It merges the base in: `--ff-only` when behind or holding nothing the base lacks, an ordinary merge when diverged, never a rebase because the branch may be pushed; a conflict aborts the merge and stops with the paths. The return carries `createdBranch`.
- **Finish lands the build only with every task ticked, the wall green and the tree clean**: the base brought up to date and merged in when it moved, unless the base's `spec.md` differs from the build branch's, which stops the run; the wall again when that brought anything; then `git push origin HEAD:<base>`, which origin takes only as a fast-forward — refused, it goes back to the sync, up to 3 landings in all — the local base fast-forwarded, the local build branch deleted, and the one on origin deleted only when it is an ancestor of the landed head. A landing that does not happen is a stop at finish, with the branch checked out and pushed.
- **`.specify/feature.json`** is pointed at the resolved feature, the one file preflight writes: spec-kit's scripts resolve the feature from `SPECIFY_FEATURE_DIRECTORY`, then from that file, never from the branch name.

## Base-branch discovery

How preflight reads the sources of the base branch that [SKILL.md](SKILL.md) lists:

- The file read is the root `CLAUDE.md` as committed at `HEAD` of the branch the run starts on; a backend's `CLAUDE.md` and the working tree are not read. A branch cut before the line was committed holds none; start from the base branch, or pass `baseBranch` once.
- **A line that is found and does not name a local branch is a stop, never a fall-through:** a line not in the exact form (bulleted, numbered, indented, emphasised, unquoted, trailing prose), two lines naming different branches, or a line naming a branch that does not exist locally each end the run at preflight, naming the line.
- **An `origin/HEAD` that names no local branch is unresolved too** (`git clone -b dev` records `origin/main` and makes no local `main`); the stop names `git branch <name> origin/<name>`.
- Nothing is fetched. Where `baseBranch` is absent, one read-only agent (`base branch`) runs a `grep` over `git show HEAD:CLAUDE.md`, `git symbolic-ref --short refs/remotes/origin/HEAD` and `git for-each-ref` over the local branches and returns their output verbatim; the script parses the line and applies the precedence (`resolveBase()`). The return carries `baseBranch` and `baseBranchSource` — `arg`, `claude-md`, `origin-HEAD` or `fallback`.

## Inputs a later start checks

**A later start checks the artifacts it reads on the branch the run would work on, before any branch is made.** `plan.md` from `review-plan` or `tasks`; `plan.md` and `tasks.md` from `analyze`, `implement` or `converge`; `tasks.md` from `finish`. A planning start reads them on the up-to-date base, a build start on the base's commit (`git cat-file -s <base>:<path>`) before any branch is made, and the build-branch step again after the sync. A missing or empty one stops the run with nothing committed, naming the files and the `from` that writes them.

## Spec questions and the restart after an answer

No stage writes `spec.md`, and a finding a planning stage can close only by a change to the spec is a question for the domain expert ([SKILL.md](SKILL.md)). How the stages handle that:

- The plan-review fixer, the tasks stage and the analyze remediator return such a finding in `specChanges` as a question — plain words, no technical terms — with the answer they recommend, then work on that answer and record in `research.md` that the reading waits on the domain expert. The script collects the questions across the three stages and hands the list to every later reader and fixer so none is asked twice.
- `QUESTIONS.md` is on the base branch beside the spec, and carries one line for the domain expert to paste into Claude Code opened in the project: stock `/speckit-clarify`, told the feature directory, to update the base branch from origin first, to write the answers as a new feature with `/speckit-specify` instead when origin has the build branch or every task is ticked, otherwise to ask the file's questions first, and at the end of every session, whatever is left, to commit `spec.md` on the base branch and push — on a refused push `git pull --rebase` and push again, on a conflict stop and say so in plain words — so the domain expert runs no git. Clarify takes the file as its prioritisation context, asks up to five questions per run, each with a recommended answer, and writes the answers into the spec.
- **A finding whose remedy changes behaviour an earlier feature's spec specifies is still a question for this feature's spec**, phrased as a change this feature makes to that feature and naming it. The earlier feature's spec is left as the record of what was built.
- **The build asks the domain expert nothing.** Every question that could change the spec is asked during planning. Converge and the forced append follow the reading the plan recorded, one waiting on the domain expert's answer included; where neither the spec nor the plan decides a reading, they decide it from the spec, the constitution and the code and have the task record it in `research.md`.
- The domain expert works on the base branch and keeps working there while the run goes on. A planning run reads the spec as preflight pulled it; a later planning start that pulls a changed spec, or a planning run whose final pull brings one, is a `needs-human` exit whose restart is `from: "review-plan"`. A build whose base spec changed stops and merges nothing.
- Every agent is told to ignore a `CLAUDE.md` or other project file that tells it to fetch, pull, check out, rebase or push, and to run only the git steps its prompt names.
- Preflight refuses on a `[NEEDS CLARIFICATION]` marker still in the spec and lists them: those are the domain expert's to answer with `/speckit-clarify`.
- An implement agent that can see no fix but a spec edit leaves the task unticked and quotes the requirement. The wall-repair prompts name editing the spec among the moves that may never buy a green wall.
- Traceability: an FR or SC is cited `<NNN>/FR-nnn` outside the feature directory; a row in `specs/trace-waivers.tsv` is authored at the tasks stage and nowhere else.

After the domain expert has answered into the spec, `plan-feature` restarts at `from: "review-plan"` ([SKILL.md](SKILL.md)). That start's first review is told the spec may have changed since the plan was written; a plan artifact that disagrees with the current text is a blocking finding, and the fixer brings it into agreement in place; a reading `research.md` records as waiting on the domain expert that the spec still does not answer goes back to them as a question, unless a person left it open; tasks, analyze and every later stage run again. Every exit whose whole remedy is a spec change — the questions stop after analyze, preflight's exits for a spec that moved under a later start, and preflight's refusal while `QUESTIONS.md` holds an open question — returns `restartFrom: "review-plan"`, and its handoff names the same stage. Preflight's missing-input exit restarts at `plan` only where `plan.md` itself is missing.

**When that restart reaches the tasks stage over work already done, `tasks.md` is updated in place and never regenerated.** Preflight lists the file's tasks, ticked and open, whenever the tasks stage will run; where any is ticked, `/speckit-tasks`' generation does not run.

- A ticked task whose requirement, criterion or plan decision is unchanged stays ticked, convergence and forced convergence phases included.
- A ticked task whose requirement changed is unticked with its reason: `- [ ] T014 … (reopened: <what changed>)`.
- A task no longer needed, ticked or not, is marked removed and never deleted: `- ~~T015~~ (removed: <reason>)`. Its id counts toward the maximum and is never reused; every stage that reads `tasks.md` is told such a line is not a task. **The removed line is one line and names no `FR` or `SC` id**, because the traceability gate reads every id anywhere in `tasks.md`. An id the edited spec no longer defines leaves every line of `tasks.md`, and a new task takes it out of the code, tests and waiver rows that still cite it.
- New work gets new unticked tasks with ids after the maximum, in the phase it belongs to; the update ticks nothing.
- **A parse-only reader certifies the update:** every task preflight saw ticked must come back ticked, reopened with a reason, or removed with a reason; every one it saw open must come back open or removed with a reason. A ticked one unticked without a reason, any one gone, or an open one ticked stops the run at tasks. A first run, with no ticked task, generates `tasks.md` as usual.

## The tier of each stage

The rows of the `TIERS` table in `workflow.mjs`, with the reason for each; [SKILL.md](SKILL.md) states how a row is changed for one run.

| Stage | Tier | Why this tier |
|---|---|---|
| check-deferrals | Sonnet low | a text search of `spec.md` for each deferral quotation |
| preflight, finish | Sonnet medium | long step-by-step git and shell checklists; the return value is a list of facts, the one judgment preflight meets (several candidate directories) is one it refuses, and origin takes finish's landing only as a fast-forward |
| phases | Sonnet medium | parses `tasks.md`; a reader at low effort can stop short on a long file |
| handoff | Sonnet medium | writes files whose whole text the script hands it, commits, pushes; also pushes the base branch after planning |
| plan | Opus xhigh | the one decision-heavy pass; every later stage inherits its errors |
| review-plan | Opus xhigh | the refutation that stands in for the human, at the same effort as the pass it refutes |
| fix-plan, remediate (critical) | Opus high | edits that may reach the constitution, and the two rows that decide a finding needs a spec change; a fix that misses sends another round to an xhigh review |
| analyze | Opus high | cross-checks spec, plan and tasks and grades what it finds, above the medium passes that wrote the tasks; the last check before the build |
| tasks, remediate | Opus medium | decomposition, and repairs that analyze checks again |
| implement, one agent per phase | Opus medium | a bounded context per phase; the wall and converge are the checks |
| converge | Opus high | reads the whole implementation and grades every gap on `/speckit-converge`'s Step 5 scale, above the implement pass it checks; raise it to xhigh with `args.tiers` when converge misses a gap a person can see |
| reconcile-tasks | Opus medium | brings `tasks.md` to a known state after a failed forced append; must return `unsure` rather than guess, and its verdict is certified by the `phases` row |
| force-append | Opus medium | writes one task per finding from findings, not from a finished document, so a paraphrase becomes a task that closes on something else |

Sonnet goes to stages that run steps the prompt spells out and judge nothing: low for a single search, medium for a checklist or a verbatim write. Opus goes to every stage that judges or writes an artifact or code: medium where a higher-effort pass or the wall checks the output; high to the checks and to the fixes of plan-level findings; xhigh to plan and its refutation only, the two stages the rest of the run derives from.

## A gate is a fresh-context refutation, not a human

**Where spec-kit pauses for approval, a review agent with no memory of the writing refutes the artifact and returns findings as data; a fix agent applies them; the review runs again. The loop stops the run only on a survivor — a blocking or major finding that restates one an earlier fix round was handed. At its round cap it applies the last review's findings, runs one final review over that fix, and goes on with the final review's findings reported open.**

- Review-plan reads `spec.md`, every plan artifact, the constitution, the project rules and the code the plan touches, and reports every requirement no design element realises, every gate or article the design violates, and every contract that contradicts the schema. A requirement no plan can realise is reported as a change to the spec, which the fixer returns under `specChanges`.
- A constitution amendment is proposed or applied only when it passes the constitution's admission test — the rule binds two or more features, or a table the feature does not own; otherwise the finding is against the plan.
- **The script decides a survivor from a label.** From round two the reviewer gets the numbered list of every finding an earlier fix round was handed and returns `repeatOf` per finding. A finding restates an entry when the same requirement, invariant, property or contradiction at the same place is still unmet, however worded — including where the fix swapped the mechanism for one that fails the same way, or declared, narrowed or accepted the gap instead of closing it; a defect the fix introduced elsewhere is new. Exact identity (artifact, location, problem, normalised) counts too; a `repeatOf` naming no entry is ignored. The exit names each survivor with the round that handed it, and carries as `skippedByThatFix` what that round's fix agent declined and why.
- **After the cap fix nothing is applied without a review.** The final review, `review-plan <max + 2> (final)`, stops only on a survivor; its other findings are returned as `reviewPlan.ended: "round-cap"`. Its open blocking and major findings are handed to the first analysis, which returns each that still holds as its own finding, a blocking one graded no lower than `HIGH`, so a remediation applies it and the next analysis reads the fix.
- A loop runs at most `max + 1` fix rounds and `max + 2` reviews, plus a minors pass where a review approves with only minor findings (applied once, not re-reviewed).
- The analyze loop has the same rule on `CRITICAL` and `HIGH`, with `maxAnalyzeRounds` and `analysis.ended`. A `MEDIUM` or `LOW` that restates an entry is not a survivor in either loop.

## Analyze goes back to the artifact it names; converge goes back to implement

**A finding is resolved by editing, in place, the artifact it names — never by re-running the command that generated it (which regenerates the file and discards every review fix), and never by editing the spec.** The analyze remediator adds tasks with new ids for a coverage gap, changes the plan for a violation, touches the constitution only when the finding says the constitution is wrong, and returns under `specChanges` what only `spec.md` can close; then analyze runs again. `/speckit-converge` appends one phase of tasks and returns every gap it found, graded `CRITICAL`, `HIGH`, `MEDIUM` or `LOW` by its Step 5 rule; the next implement agent runs that phase alone; converge runs again.

**The severity floor is the converge loop's only stop test.** The loop ends on the first round whose findings hold nothing above `args.severityFloor`, and the return says whether that round appended tasks (`severity-floor`) or nothing (`converged`). Legal values: `NONE` (default; ranks below every severity, so the loop tolerates nothing), `LOW`, `MEDIUM`, `HIGH`. `CRITICAL` is refused, because `/speckit-converge` grades a constitution MUST violation there and the floor would tolerate everything. A round that appends tasks and grades nothing counts as above the floor.

- **A round that reports converged while grading a finding above the floor is not a human question: the loop appends those findings itself and implements them.** One `force-append` agent receives the findings rendered by the script, appends one task per finding as `## Phase N: Convergence (forced round n)` in `/speckit-converge`'s append format, and commits `tasks: forced convergence round n`; the phase goes through the same implement agent and wall gate as any other.
- **A forced task is closed by the fix and by nothing else.** Its text offers no route that closes it by recording why it was not done, and a finding about an absence is closed by a check that fails when the absence stops being true. A fix is blocked in exactly two cases: a numbered requirement or a constitution article forbids it, a fix that would need an edit to `spec.md` included, quoted with its id; or it needs a system outside the repository that does not exist. "The toolchain cannot express it", "a deployment decision", "the plan already names it as a gap" and "the file is append-only" are not blockers. A blocked task stays unticked and comes back in `blocked`; after the second pass every phase gets, the run exits `needs-human` with every other task fixed and the blockers in the handoff.
- **A finding is forced at most once.** Identity is severity, location and summary, normalised, or the assessment's own `repeatOf` label against the numbered list of what the run already forced. The forced set is returned as `converge.forced`. A forced round runs inside the slot of the round that found it, so `maxConvergeRounds` stays the single bound.
- **A finding that comes back above the floor after its forced round is the `needs-human` exit**, and the handoff says the loop already appended, implemented and wall-checked it.
- **`maxConvergeRounds`, not the floor, ends a long run**; raise the cap for more passes. The cap is followed by one assess-only round that appends and commits nothing; its findings are the ones the run carries — under `"round-cap"`, open, when it grades anything above the floor, otherwise `"severity-floor"`, or `"converged"` at floor `NONE`. A `round-cap` goes to finish, where the wall decides. Under `NONE` a run usually ends at the round cap or at `needs-human`; the wall plus the reported findings say the feature is done.

**A deferral written into `spec.md` wins over forcing.** A converge finding against something `spec.md` itself defers, puts out of scope or leaves to a later feature is not forced, does not count against the floor and is never a survivor: the assessment returns it with `deferredBy` quoting that text, and the run reports it under `converge.deferred`. **The quotation is checked first**: one `check-deferrals` agent searches `spec.md` for each new quotation, whitespace and Markdown emphasis aside; one it does not find is dropped, the finding is handled like any other, and it is listed under `converge.deferralsRefused`. Only `spec.md` counts: a scope boundary or deferral in `plan.md`, `tasks.md`, `research.md`, `docs/GATES.md` or `specs/trace-waivers.tsv` exempts nothing, because those were written from the spec by the run.

## Unattended means the agent decides by a written rule

**Every question a speckit skill would put to a person is answered by the rule in that stage's prompt, and the answer is written into the artifact.**

- Preflight establishes the feature and the branch rather than asking, on every entry, restarts included. A run given `featureDir` holds preflight to it: the prompt names that directory and no way to find another, and a return naming another or none is asked once more, then stops.
- Plan decides each open question from the spec, the constitution and the code and records it in `research.md`. **A reading the plan decided stands: the tasks, remediate, converge and force-append stages write no task whose completion waits on a person** — an owner's answer, a `/speckit-clarify` session, a sign-off. During planning a question only the domain expert can answer goes to `specChanges`; converge and force-append ask nothing.
- Implement proceeds past an unchecked checklist and lists the items. Analyze returns findings instead of offering remediation.
- **A run never hands back work it could have done itself: every escalation is something the loop attempted and failed at, or something it is not authorised to do.** A red wall gets one fresh-context repair pass before it escalates; a phase with tasks left unchecked gets one second pass over exactly those ids. Three implement agents per phase is the ceiling. A red wall at `finish` is repaired the same way, and **the re-check is a second `finish` agent: an agent that repairs a gate may not declare it green.**
- **No gate is ever weakened to make a wall pass.** The repair prompts forbid skipping, disabling, quarantining or deleting a test; a suppression, exclusion, baseline entry, waiver row or ignore comment; an edit to the feature's `spec.md`; a lowered threshold or coverage figure; a relaxed or removed gate; an edit to the wall script, the build file or any gate configuration; a force flag. Where those are the only route, the agent changes nothing and returns the wall red.
- **A failed forced append is reconciled, not escalated.** One reconcile agent reads `tasks.md` against git — an uncommitted change to it at that point is the append's own partial write — and brings it to wholly absent or wholly present; the parse-only `phases` reader certifies that state. Present: the loop implements it. Absent: one retry of the append. The reconcile writes only `tasks.md`, never ticks or unticks a task, touches only this round's forced phase, and returns `unsure` rather than guess.

## What stops the script

Each stop goes to the launching session first; [SKILL.md](SKILL.md) says which reach a person and how the session resolves the rest.

- Preflight: no resolvable base branch; a base-branch line not in its one form, or naming no local branch; a base that cannot be brought up to date from origin, or a local base holding commits origin lacks; a feature that cannot be resolved; zero or several candidate directories; a `featureDir` given that does not exist or holds no non-empty `spec.md`; a preflight agent that, asked twice, returns a feature directory other than the `featureDir` the run names; a planning start while the feature's build branch holds commits the base lacks; a merge conflict between the base and the build branch; a base `spec.md` that differs from the build branch's, or, before a build branch exists, from the one the plan review recorded; a repository not ready (dirty tree, detached HEAD, missing speckit skill); on every start, whatever its `from`, a base branch without `scripts/check-traceability.mjs` or `scripts/check-traceability.selftest.mjs` at the project root or without a `scripts/wall-checks.txt` line listing each, whose fix is `/init-pipeline`; no definition-of-done command; a `[NEEDS CLARIFICATION]` marker in the spec; a spec the update changed under a planning start later than `review-plan`, or one the plan review did not record; a later start whose input artifacts are missing on the branch it would work on; a start at implement or later while `QUESTIONS.md` holds an open question; a preflight that reports no problem while on the wrong branch — off the base for planning, on it for a build — or a detached HEAD.
- Then: a tasks update the certification rejects; an open question for the domain expert, after analyze; a survivor at review-plan or analyze; a conflict pushing the planning commits, a push still refused after 3 attempts, or a base spec after their final pull that is not the one the review recorded; a build branch that cannot be made or checked out, a merge conflict with the base or a differing base spec in the build-branch step; a wall still red after its repair pass, at a phase or at finish; a task two implement passes decline to tick; a converge finding that survives its forced round; a reconcile that cannot establish what is in `tasks.md`, or a reconcile and a reader that disagree; a forced append whose retry failed too; an appended phase two parse-only reads do not return; at finish, unticked tasks, a merge conflict with the base, a base spec that changed during the build, a base that cannot be updated, or a landing still refused after 3 attempts.
