# Build a feature — the spec-kit cycle from a finished spec, with no human gate

**Premise, shared with every skill in this set:** the code is written by LLM agents and no human reads it line by line. The consequence for a feature is that the human gates spec-kit puts between its commands — *review the plan before tasks* — are the last place a person reads anything, and on 2026-09-16 those reviews found blocking defects only because the reviewer was a fresh context, not a person. This skill keeps the fresh context and drops the person: one deterministic script, one subagent per stage, a refutation review where each gate was, and a converge loop that ends at a severity floor, which by default tolerates no finding at all — because on the one run that tested it (2026-09-18) converge had no fixed point, and the owner's decision the same day is that a tolerated finding is a finding left open. **The one thing it does not automate is the specification.** A domain expert writes `spec.md` in the project with stock `/speckit-specify` and `/speckit-clarify`; this script starts at `plan` and never writes that file.

## Run the workflow; orchestrate nothing yourself

**Call the Workflow tool with this skill's script, from the base branch or from the feature branch, once the feature's `spec.md` is written, and run no spec-kit command from your own context.**

```
Workflow({
  scriptPath: "${CLAUDE_SKILL_DIR}/workflow.mjs"
})
```

**Nothing is required.** Preflight discovers what the run is for and then puts the repository where the build belongs. The feature directory comes from `args.featureDir`, else from the checked-out branch name (`feature/<NNN>-<name>` or `<NNN>-<name>` → `specs/<NNN>-<name>`), else — when the run was started on the base branch — from the one directory under `specs/` holding a written `spec.md` and no `plan.md`, the feature specified and not yet planned; `.specify/feature.json` is consulted last and never overrides, because it is git-ignored machine-local state that names whichever feature this checkout last ran `/speckit-specify` on. Two candidates or none is a `needs-human` exit listing them, never a pick. The definition-of-done command comes from the project's `CLAUDE.md`, and so, since 2026-09-25, does the base branch, where the file states it in one line (next paragraph), and everything below keys off it. **A run started on the base branch checks out the feature branch — `args.branch`, else an existing `feature/<dir>` or `<dir>` local or remote, else a new `feature/<dir>` cut from the base — and every run whose branch is not the base then merges the base into it.** **A run that starts at a later stage on the base branch — `converge-feature` closing out a feature implemented on the trunk — does the same with one difference, because the work it resumes lives on the base branch: preflight refuses a dirty tree, then makes the feature branch at the base branch's HEAD, or moves an existing one of that name forward to it where it is an ancestor, and checks it out, so no stage commits on the base branch (owner's decision, 2026-09-25).** An existing feature branch holding commits the base lacks is a preflight problem rather than a pick where the base branch also holds any of the feature artifacts the run reads, since the feature's work is then in two places; where the base holds none of them the work is on that branch, and preflight checks it out instead (below, 2026-09-25). The return value carries `createdBranch`, and the handoff's table says when the run made the branch. The rejected default is to stop and ask: a person step for a mechanical act a full run already performs. Until that day such a run stayed on the trunk and its converge, implement and fix agents committed there, while this skill said the run never does. **Such a close-out passes `featureDir`:** on the base branch discovery answers only with the one specified-but-unplanned directory, never a feature already planned there, so without it the run resolves that other feature and stops on its missing `plan.md`, and the stop says so (2026-09-25). The merge into the feature branch is why the experts can keep editing `spec.md` on the trunk while the build runs: `--ff-only` when the branch is merely behind, an ordinary merge when the two diverged, never a rebase because the branch may be pushed, and a conflict aborts the merge and stops the run with the paths. ## The spec is fixed input, and no stage of this run edits it

**`<featureDir>/spec.md` is the fixed input to the run: every stage reads it, no stage — no review fix, no remediation, no implement pass, no repair, no forced convergence task — writes it, and a finding whose only remedy is a change to the spec ends the run as `needs-human` with that change named. Where it goes next is the resolution rule below: the session that launched the run applies the change where it holds that recommendation with high confidence, and otherwise takes it to the expert the change belongs to: a domain decision to the domain expert, in writing, which reopens the spec handoff as `/build-feature-prepare`'s reopen rule does; a technical one to the technical expert running the build.** The feature is specified by a person before the run starts (owner's decision, 2026-09-21): the expert runs `/speckit-specify` and `/speckit-clarify` in the project and writes the spec himself, and this script begins at `plan`. Between the two runs the spec handoff (2026-09-26): `/spec-handoff-questions`, a fresh-context, read-only reading of the spec, writes its questions to `<featureDir>/HANDOFF-QUESTIONS.md` under Domain, Domain+Technical and Technical; the domain expert alone, both experts together, and the technical expert alone answer them into the spec (`/spec-handoff-domain`, `/spec-handoff-joint`, `/build-feature-prepare`), and the technical expert commits the result and launches this run; no stage of this run reads that file. Ownership of the spec follows the handoff: its Domain content is the domain expert's, its Domain+Technical content is both experts' jointly, and its Technical answers are the technical expert's. **He works on the base branch, and he keeps working there while the build runs** — so the run makes its own feature branch, merges the base into it on every entry, and picks up each later edit to the spec that way. A spec change that arrives after the plan was written is a `needs-human` exit whose restart is `from: "review-plan"`, because `plan.md`, `tasks.md` and the code were all derived from the old text and no stage after the plan review reconciles that; a start at `plan` or `review-plan` reads the new text itself and carries on. Five consequences carried in the prompts. Preflight refuses on a `[NEEDS CLARIFICATION]` marker still in the spec and lists them, because those are the domain expert's to answer with `/speckit-clarify` and a plan written against an unresolved marker decides by accident exactly what the marker exists to decide. The plan-review fixer, the tasks stage and the analyze remediator each carry a `specChanges` field beside `skipped`, and the converge assessment and the forced append carry the same field (2026-09-24): a finding they cannot resolve in the artifacts they may write goes there, the run stops, and the build restarts at `review-plan` once the spec is changed. An implement agent that can see no fix but a spec edit leaves the task unticked and quotes the requirement — the third of the three blockers a forced convergence task admits. And the wall-repair prompts name editing the spec among the moves that may never buy a green wall, beside deleting a test and relaxing a gate, because reshaping the spec to fit the code deletes the run's own definition of done. The local traceability chain is unchanged — an FR or SC cited `<NNN>/FR-nnn` outside the feature directory, a row in `specs/trace-waivers.tsv` authored at the tasks stage and nowhere else — and the upstream-provenance layer the service repos dropped the same day is gone from every prompt with it. The default an agent reaches for is to *align the spec* with what it has decided or built: rejected, because the spec is the only artifact in the run that no stage of the run authored, which is the whole of its value as an oracle — an artifact the run may rewrite cannot refute it.

**After the spec is edited — by the expert the change belongs to, or by the launching session under the resolution rule — the build restarts at `from: "review-plan"`, whatever stage stopped, and never at `plan` unless a person asks for a new plan (owner's decision, 2026-09-24).** That start reads the plan already on the branch against the spec's current text: its first review is told the spec may have changed since the plan was written, a plan artifact that disagrees with the current text is a blocking finding, and the fixer brings that artifact into agreement in place; tasks, analyze and every later stage then run again over the repaired plan. Every exit whose whole remedy is a spec change — the `specChanges` exits at review-plan, tasks, analyze and converge, and preflight's exit for a spec the sync moved under a later start — returns `restartFrom: "review-plan"`, and its handoff's restart paragraph and reason name the same stage; preflight's missing-input exit restarts at `plan` only where `plan.md` itself is missing. **The rejected default is the restart at `plan` this skill named until that day**, while rejecting a re-run of plan everywhere else: `/speckit-plan` regenerates `plan.md` whole and discards every review fix before it, and on eight such restarts the regenerated plan hit a fresh review-plan cap five times — `wf_c65ab41b-8a6`, `wf_9ecfdaff-a93`, `wf_11cbb069-ff1`, `wf_85172f44-a39`, `wf_c3abfa9f-b08` — with findings that, in one session's own words, repeated nothing earlier because the plan was new (run ledger, sweep 2). Unrun: no run has restarted this way.

**When that restart reaches the tasks stage over work already done, `tasks.md` is updated in place and never regenerated (owner's decision, 2026-09-25).** Preflight lists the file's tasks, ticked and open, whenever the tasks stage will run; where any is ticked, the stage does not run `/speckit-tasks`' generation. A ticked task whose requirement, criterion or plan decision is unchanged stays ticked, every task of a convergence or forced convergence phase included. A ticked task whose requirement the change altered is unticked with its reason at the end of its line — `- [ ] T014 … (reopened: <what changed>)` — so implement builds it again. A task the revised spec and plan no longer need, ticked or not, is marked removed and never deleted: `- ~~T015~~ (removed: <reason>)`. Spec-kit's checklist format has no state for it, and both states it has are wrong — an open box is work implement would run and the service repos' traceability gate counts as in flight, a ticked one claims work nobody did — so the box goes, the line and its id stay, and `/speckit-converge`'s append contract, which takes the next id from the maximum in the file, never reuses it; the phase reader, analyze, converge, implement, the analysis remediation, the forced append and finish are each told that such a line is not a task and that its id counts toward the maximum. **The removed line is one line and names no `FR` or `SC` id** — the task's text and continuation lines go, and are in the update commit's parent — because that gate reads every id anywhere in `tasks.md`, not only on task lines: an id the spec no longer defines is a failing citation, which is the commonest reason a task is removed, and one it still defines counts as named by a task and hides a requirement no live task plans (adversarial review, 2026-09-25, against copies of the gate). For the same reason an id the edited spec no longer defines leaves every line of `tasks.md`, and a new task takes it out of the code, tests and waiver rows that still cite it. New work gets new tasks, unticked, with ids after the maximum and in the phase it belongs to, and the update ticks nothing. Implement then runs only what is open, as it always did. **The update is certified by a parse-only reader, not by the agent that made it**: every task preflight saw ticked must come back ticked, reopened with a reason, or removed with a reason, and every one it saw open must come back open or removed with a reason; a ticked one unticked without a reason, any one gone, or an open one ticked stops the run at tasks before analyze, because implement would redo work on nobody's decision, skip work nobody did, or lose the record of a task. A renumbering shows as a missing id and stops the same way; a reworded task does not, and is read off the update commit's diff. A first run is unchanged: with no ticked task the stage generates `tasks.md` as before, from the same prompt. The rejected default is that regeneration applied to every run, as it was until that day: `/speckit-tasks` writes the file whole with every task unticked, so a restart after a spec edit on an implemented or converged feature — the restart `converge-feature`'s spec exits name — implemented every phase again over code that exists, and its forced convergence phases left the file. Unrun: no run has taken the update; it is modelled against a stub of the Workflow sandbox.

## Each stage runs on the tier it earns

**Take the model and effort of every stage from the `TIERS` table in `workflow.mjs`, and take every row from the roster: Opus at low, medium or high effort, and no other model (owner's decision, 2026-09-23). Change a row for one run with `args.tiers`, never by editing the table.** The model is the alias `opus`, which resolves to the newest Opus — Opus 5.5 as of 2026-09-23 — and is not pinned to a full id, because the Workflow authoring reference names no accepted values for `agent()`'s `model` and the Agent tool's `model` takes aliases only. No other pair exists for this script: a row on Haiku, Sonnet or Fable, or on `xhigh` or `max`, fails the run before its first agent starts, whether it came from the table or from `args.tiers`.

| Stage | Tier | Why this tier |
|---|---|---|
| preflight, phases, finish | Opus low | shell commands and parsing; the return value is a list of facts. Preflight is the widest of the three — it resolves the feature by a written order, checks a branch out or makes one, merges the base in and writes one git-ignored file — and every step of it is a named command with a stated outcome, the one judgment (which of several candidate directories) being the one it is told to refuse rather than make |
| handoff | Opus low | writes one file whose whole text the script hands it, commits it, pushes it; nothing in the stage is a judgment |
| plan | Opus high | the one decision-heavy pass; every later stage inherits its errors, so it takes the most effort the roster admits |
| review-plan | Opus high | the refutation that stands in for the human; an adversarial review of the pass every later stage inherits, at the same effort as the pass it refutes |
| fix-plan, remediate (critical) | Opus medium | edits that may reach the constitution, and the two rows that decide a finding needs a spec change |
| tasks, analyze, remediate | Opus medium | decomposition and cross-checking of artifacts a high-effort review already passed |
| implement, one agent per phase | Opus medium | a bounded context per phase; the wall is the check, and effort here buys fewer red-wall retries |
| converge | Opus medium | reads the whole implementation, up to six rounds and one assess-only round after them, grades every gap it finds on `/speckit-converge`'s own Step 5 scale, and what it appends is implemented and then wall-checked; the row to raise with `args.tiers` when a converge misses a gap a person can see, or grades one below a raised floor |

| check-deferrals | Opus low | searches `spec.md` for each deferral quotation a converge round offers and the run has not checked yet; a text search with no judgment in it, whose answer decides only whether a finding keeps its exemption from forcing |
| force-append | Opus medium | authors one task per finding a converge round graded and declined to append, each closable by the fix alone; not a clerical row like `handoff` — the script hands it findings, not a finished document, and a paraphrase here becomes a task that closes on something else |

Effort is the only axis left, and it is spent where errors propagate. Medium goes to every stage that writes an artifact or code, because each is either reviewed by a higher-effort pass or checked by the wall. ## A gate is a fresh-context refutation, not a human

**Where spec-kit pauses for approval, a review agent with no memory of the writing is prompted to refute the artifact and returns findings as data; a fix agent applies them; the review runs again. The loop stops the run on a survivor and on nothing else of its own — a blocking or major finding that restates one an earlier fix round was handed — and at its round cap it does not stop: it applies the last review's findings, runs one final review over that fix, and goes on to tasks with the final review's findings reported open (owner's decision, 2026-09-24).** The artifact that gate stands over is the plan, and its oracle is outside the run: review-plan reads `spec.md` — which this run did not write and may not change — every plan artifact, the constitution, the project rules and the code the plan touches, and reports every requirement no design element realises, every gate or article the design violates, and every contract that contradicts the schema. A requirement no plan can realise, because the spec contradicts itself or the constitution or the code, is reported as what it is: a change to the spec, which the fixer returns under `specChanges` rather than making. A constitution amendment is proposed or applied only when it passes the constitution's own admission test — the rule binds two or more features, or a table the feature does not own; a rule about the feature's own tables is a plan decision and the finding is against the plan. Rejected, 2026-09-17: without the test, two plans grew Article VII from three sub-articles to fourteen, most of them one feature's schema written as law, and the third feature's spec had to start by amending three of them.

**A survivor is decided by the script, from a label, not from the reviewer's prose.** From the second round on, the reviewer is handed the numbered list of every finding an earlier fix round was handed and returns `repeatOf` per finding — the entry it restates, or 0. A finding restates an entry when the defect that entry named is still there: the same requirement, invariant, property or contradiction at the same place is still unmet, however it is worded, including where the fix swapped the mechanism for one that fails the same requirement in a new way, and where the fix declared the gap, narrowed the requirement or recorded it as accepted instead of closing it; a defect the fix introduced at another place is new. Exact identity — artifact, location and problem, normalised — counts too, and a `repeatOf` naming no entry is ignored. That is converge's forced-once rule one stage earlier, with converge's own label as its precedent: the loop tried once, the attempt did not take, and what is left is a decision, so the exit's `why` names each survivor with the round that handed it, and its detail carries, as `skippedByThatFix`, what that round's fix agent declined and why — *applied and did not take* and *declined with this reason* are different decisions for whoever resolves the stop, and the reason is otherwise only in the machine-local journal. ## Analyze goes back to the artifact it names; converge goes back to implement

**A finding is resolved by editing, in place, the artifact it names — never by re-running the command that generated that artifact, and never by editing the spec.** `/speckit-analyze` finds coverage gaps, contradictions and constitution violations across spec, plan and tasks; the remediation agent adds tasks with new ids for a coverage gap, changes the plan for a violation, touches the constitution only when the finding says the constitution is what is wrong, and returns under `specChanges` the findings that can only be closed in `spec.md` — which stops the run; then analyze runs again. `/speckit-converge` appends one phase of tasks and returns every gap it found — appended or not, actionable or not — graded by that skill's own Step 5 severity rule, whose four values `CRITICAL`, `HIGH`, `MEDIUM` and `LOW` are the same four the analyze schema carries, so no second vocabulary enters the run; the next implement agent runs that phase alone; converge runs again. **The severity floor is the loop's only stop test: the loop ends on the first round whose findings hold nothing above the floor, and the return value says whether that round had appended tasks (`severity-floor`) or nothing (`converged`). The floor is `args.severityFloor`, and it is `NONE` by default — `NONE` ranks below every graded severity, so every finding the assessment grades is above it and the loop tolerates nothing. The legal values are `NONE`, `LOW`, `MEDIUM`, `HIGH`; a run raises the floor to `LOW` or `MEDIUM` when it wants the loop to stop at the gaps a person would notice, and that is the one setting that changes when the loop stops. `CRITICAL` is refused rather than offered: `/speckit-converge` Step 5 grades a constitution MUST violation there, so a floor at `CRITICAL` tolerates every finding the scale has and ends the loop after one round.** Under `NONE` the exits mean this. `converged` is the only clean stop and requires a round that appended nothing *and* graded nothing. **A round that reports converged while still grading a finding above the floor is not a human question: the loop appends those findings itself, as a forced convergence round, and implements them.** `/speckit-converge` Step 7 calls a round converged on *no **actionable** findings* and Step 4 surfaces gaps for awareness, so a graded finding on a `converged` return is that skill judging a gap non-actionable — which is the judgment the floor exists to decline. A floor that declines it owes the work it withheld, so one `force-append` agent receives the findings the script filtered, rendered by the script and never paraphrased, appends one task per finding as `## Phase N: Convergence (forced round n)` in `/speckit-converge`'s own append format, commits `tasks: forced convergence round n`, and the appended phase goes through the same implement agent and the same wall gate as any other. The one finding it writes no task for is one only an expert can answer: it appends nothing, returns that finding under `specChanges` and the run stops (2026-09-24), because the only task it could write would wait on a person, which the *Unattended* section bans. **A forced task is closed by the fix and by nothing else (owner's rule, 2026-09-20: a floor of `NONE` means a LOW finding is fixed).** The task text names the work and offers no route that closes it by recording why it was not done; a finding about an *absence* ("this capability contains no approval gate") is closed by the check that fails when the absence stops being true, not by a citation and not by a rationale. The implement agent on a forced phase is told the same, and that a fix is blocked in exactly three cases — a numbered requirement or a constitution article forbids the change, quoted with its id; the change needs a system outside the repository that does not exist; or the only fix is an edit to `spec.md`, which is an expert's. "The toolchain cannot express it", "a deployment decision", "the plan already names it as a gap" and "the file is append-only" are named in the prompt as *not* blockers, because each was claimed on `product-catalog` 004 and each was fixed by hand the same day. A blocked task stays unticked and comes back in `blocked` with its blocker; after the second pass every phase gets, the run exits `needs-human` with every other task fixed and committed and the blockers in the handoff — a decision about the spec, not work the loop withheld. The default an agent reaches for, and the one this skill shipped until 2026-09-20, is a second route — *or record in `convergence-rationale.md` why it is not a defect* — and on 004 every task of six forced rounds took it (evidence.md). **A finding is forced at most once.** Identity is its severity, location and summary, normalised, *or* the assessment's own label: each converge round after a forced one is handed the numbered list of what the run already forced and returns `repeatOf` per finding, because exact match alone never fired on re-typed wording — 004 forced the same thirteen findings six rounds running. That distinction is the value of the handoff: a person reading it knows the difference between nobody having tried and the loop having tried and failed. ## Unattended means the agent decides by a written rule

**Every question a speckit skill would put to a person is answered by the rule in that stage's prompt, and the answer is written into the artifact.** Preflight establishes the feature rather than asking which one — `args.featureDir`, else the branch name, else the single specified-but-unplanned directory under `specs/`, else the git-ignored `.specify/feature.json` — and then puts the repository on the feature branch and merges the base in, rather than asking whether it may. The same discovery and sync run on every entry, restarts included, so a run that starts at `converge` knows its own branch and the handoff and merge prompts do not fall back to `(unknown)` and `HEAD@{1}`. Plan decides each open question from the spec, the constitution and the code and records it in `research.md`, and **a reading the plan decided stands: the tasks, remediate, converge and force-append stages write no task whose completion waits on a person** — an owner's answer, a `/speckit-clarify` session, a sign-off — and a question only an expert can answer goes to `specChanges`, where the run stops at the stage that found it; converge and the forced append gained both the ban and the field on 2026-09-24, the same day as the other two. The default a remediating agent reached for is to turn the plan's open readings into a gating task; rejected 2026-09-24 on `reference-data` 003, where one such task (T104) stopped a run at implement after eight wall-green phases and the owner then confirmed every reading unchanged (run ledger, sweep 2). Implement proceeds past an unchecked checklist and lists the items. Analyze returns findings instead of offering remediation. A stage that has to ask stops the run: that is the `needs-human` exit, and it is the only one — what becomes of that exit is the resolution rule above, which since 2026-09-22 puts it to the launching session before it reaches anybody. **And a run never hands back work it could have done itself: every escalation is either something the loop attempted and failed at, or something it is not authorised to do** (owner's rule, 2026-09-18, and since 2026-09-22 it binds the session that launched the run as well as the loop inside it). So a red wall gets one fresh-context repair pass before it escalates — the implementing agent had already run the wall `maxWallAttempts` times inside its own context, so what is missing is a second context reading the same failure, which is this skill's premise for every review gate — and a phase with tasks left unchecked gets one second pass over exactly those ids, the shape the implement stage already had and the convergence phases did not. Three implement agents per phase is the ceiling; there is no third shape and no retry of a retry. A red wall at `finish` is repaired the same way, and **the re-check is a second `finish` agent rather than the repairing agent's own word: an agent that repairs a gate is not the one that may declare it green.** **No gate is ever weakened to make a wall pass.** The repair prompts enumerate what is forbidden — skipping, disabling, quarantining or deleting a test; a suppression, exclusion, baseline entry, waiver row or ignore comment; an edit to the feature's `spec.md`; a lowered threshold or coverage figure; a relaxed or removed gate; an edit to the wall script, the build file or any gate configuration; a force flag — and tell the agent that where the only route it can see is one of those, it changes nothing, leaves the tree as it found it and returns the wall red. A green wall bought that way is strictly worse than the escalation it would replace, and it is the one outcome this run cannot accept. **A failed forced append is reconciled rather than escalated.** When the `force-append` agent reports it could not write `tasks.md`, one reconcile agent reads that file against git — at that instant nothing else in the run has touched it since the previous round's work was committed, so an uncommitted change to it is that agent's own partial write and `git checkout` restores the committed file exactly — and brings it to one of two known states, wholly absent or wholly present, with nothing partial surviving. The parse-only `phases` reader then certifies that state independently, because the agent that cleans up is not the one that certifies the result. Wholly present means the phase was written and the agent failed only to say so, and the loop implements it rather than appending it twice; wholly absent means one retry of the append. The reconcile may write to `tasks.md` and nothing else, never ticks or unticks a task, never touches a phase other than this round's forced one, and returns `unsure` rather than a guess. Rejected, 2026-09-19: escalating a failed append on the spot, which this skill did for one day. The ground is the owner's rule again — *somebody needs to look at `tasks.md`* is not a human-only act — and the corruption risk that reasoning rested on is real but is an argument against a **blind** retry, which is not what this is.

**What still stops the script — twenty reasons, across thirty-one exits since 2026-09-25, when preflight's still-on-the-base-branch exit, the tasks update's certification exit, the unresolved-base-branch exit and the unreadable-or-stale base-branch-line exit were added; on 2026-09-24 the `specChanges` exits at tasks and converge and preflight's missing-input exit were added and the review and analyze cap exits became survivor exits.** A stop is not the same as a question for a person: each is handed to the launching session first, and only the three classes named in the resolution rule above reach anybody. Eleven are preflight's, and each is a state the run is not authorised to resolve: no base branch can be resolved — no `baseBranch`, no base-branch line in the root `CLAUDE.md`, no `origin/HEAD` naming a local branch, and not exactly one local `main`, `master`, `develop` or `dev` — which stops before preflight's own agent runs; a base-branch line in that file that cannot be read in its one form, or names a branch that does not exist locally, which stops at the same point rather than falling through; the feature cannot be resolved at all; the run was started on the base branch and two or more directories under `specs/` are specified-but-unplanned, or none is — it lists the candidates and asks for `args.featureDir` rather than picking; merging the base branch in conflicted, which the merge aborted and which is a person's to resolve on the branch; the repository is not ready — a dirty tree, checked before anything is checked out, a detached HEAD, or a missing speckit skill; no definition-of-done command, because inventing one is guessing the owner's intent; a `[NEEDS CLARIFICATION]` marker still in the spec, which the domain expert resolves with `/speckit-clarify`; a spec that the sync changed under a run told to start later than `review-plan`, whose restart is `from: "review-plan"`; a later start whose input artifacts are missing or empty on the branch it would work on, which names them and the `from` that writes them rather than running a stage over nothing, and makes no branch; and a preflight that reports no problem while the run is still standing on the base branch or on a detached HEAD, where every later stage would commit — the script's own check on the agent's report, which also takes a branch named the base branch as the base branch whatever the agent's `onBaseBranch` says. Then: a tasks update in place that a parse-only reader finds left a ticked task neither ticked nor reopened or removed with a reason, or an open task gone or ticked; a finding whose only remedy is a change to the spec, at review-plan, at tasks, at analyze or at converge — the assessment or the forced append; a blocking or major review finding, or a `CRITICAL` or `HIGH` analysis finding, that restates one a fix round was handed — a survivor, in any round, the final one after the cap included; a wall still red after its one fresh-context repair pass, at a phase or at finish; a task two implement passes decline to tick; a converge finding that survives its own forced round; a reconcile that cannot establish what is in `tasks.md`, or a reconcile and a parse-only reader that disagree about it — acting on either account deletes real tasks or leaves a duplicate phase, and neither is recoverable; a forced append whose reconciled retry failed as well; and an appended phase two parse-only reads of `tasks.md` do not return, where implementing the wrong phase is worse than stopping. Every one of them carries what was attempted and how often, and the reconcile's exits carry its quoted evidence, so nobody is sent to work out the state of a file the run has already read. A converge loop that runs out of rounds is not asking — it is reported and the run goes on to the wall, and at the default floor that is the ordinary end of a long run rather than an exception. Neither is a converge round that grades a gap and declines to append it: the loop appends that work itself and implements it, and only a finding that survives its own forced round becomes a question. **A later-stage start on the base branch is not one of them either**: a feature implemented on the trunk — `converge-feature` closing one out — gets its feature branch made at the base branch's HEAD by preflight and runs there (2026-09-25). So the only exits taken on the base branch are preflight's own, before it has moved the run: a dirty tree, a feature it cannot resolve, a feature branch that already holds work the base lacks while the base holds the feature's artifacts too, an input artifact missing on the branch the run would work on — checked before any branch is made since 2026-09-25, when until that morning preflight noted the files, made the branch and committed the exit's `HANDOFF.md` on it — and the still-on-base check. An unresolved base branch, and an unreadable or stale base-branch line, stop earlier still, before the run knows whether it stands on the base branch. None of these commits anything; the return value is the report.

(Check: a `[NEEDS CLARIFICATION]` or template placeholder left in a plan artifact is a blocking or major finding of the plan review, so it cannot survive to implement, and one left in `spec.md` is preflight's refusal — *bespoke*, the preflight and review prompts in `workflow.mjs`. `grep -n NO_TASK_WAITS_ON_A_PERSON workflow.mjs` shows the ban in the tasks, remediate, converge and force-append prompts, and `grep -n specChangesOf workflow.mjs` shows each of those stages' return read and stopping the run; whether an agent obeys the ban is read off `tasks.md` — *convention*, 2026-09-24. ## A needs-human exit leaves a file behind

**Every `needs-human` exit writes `HANDOFF.md` into the feature directory, commits it on the feature branch, and pushes it when `push` is true, before it returns.** The file is the handoff surface: it says at the top that the run stopped, who reads it first and on what terms, and then carries the stage it stopped at, the reason, the full findings rendered item by item, the branch, the round counts, the stages that ran, the definition-of-done command, the severity floor, the run's date, the arguments that restart the run at that stage, and where the run journal is kept for whoever has the machine. **It names no journal path (2026-09-24): the run id is on the Workflow tool result the launching session received, and the session records it in `RESOLUTIONS.md`.** Until that day the handoff agent took the newest journal on disk, and on 25 of 27 handoffs that named an earlier run's journal or none, because the running one is, by inference, not yet written (run ledger, sweep 2); the script has no handle on its own run id — the Workflow API gives a script none — so the rejected default of looking one up lost to a durable file stating a false path. It is written by one Opus-low agent, because the script runs in a sandbox with no filesystem and no `Date`; the document itself is rendered in `workflow.mjs` and handed to that agent finished, with one placeholder — the date — so the cheapest tier in the table cannot paraphrase a finding or drop one. The commit is by pathspec, that one file and nothing else, because the tree at a `needs-human` exit may hold the run's failing work. The gap this closes was observed 2026-09-18 on run `wf_7e4e8726-4b5`: a converge exit's three findings existed in the invoking session's tool result, a file under `/tmp` and the machine-local run journal — three places, none of them the repository, and a colleague could reach none of them.

**A failed handoff never costs the run its verdict.** A handoff agent that throws, is skipped or returns nothing leaves the full `needs-human` payload — stage, reason, findings and all — on the return value exactly as before, with `handoff.written: false` and the reason in `handoff.note`; losing the findings because a write failed is strictly worse than not writing. **An exit before a base branch or a feature directory is resolved, and any exit taken while the run is still standing on the base branch or on a detached HEAD, writes nothing and says so on the return instead.** The file is committed on the branch the run is on, and a commit on the trunk is not this script's to make: that covers every failure before preflight checked a feature branch out — a dirty tree among them, which would otherwise sweep somebody's uncommitted work into a handoff commit. Since 2026-09-25 nothing else is: a later-stage run on a feature implemented on the trunk is on the feature branch preflight made before any later exit can be taken, and writes its handoff there. A preflight refusal is in any case a repo-state fact the next person reproduces in one command rather than a finding that exists nowhere else. The red wall at `finish` is the exit that never goes through `needsHuman()` and gets the same file, on a return that keeps its own shape with `handoff` added.

(Check: `needsHuman()` is `async`, every one of its call sites is `return await needsHuman(...)`, the finish red-wall return awaits `writeHandoff` too, the whole dispatch sits in a `try` whose every failure path returns a `written: false` record rather than throwing, and the push instruction appears in the handoff prompt only when `args.push` is true — *bespoke*, `workflow.mjs`, 2026-09-18. The handoff prompt runs no journal lookup and the document carries no journal placeholder — *bespoke*, `workflow.mjs`, 2026-09-24. On a run that stopped, the feature branch's `git log` carries a `handoff: the <stage> stage stopped and needs a person` commit touching one file — *convention*, 2026-09-18.)

## A needs-human return is the session's to resolve, not to relay

**When the workflow returns `status: "needs-human"`, do not hand it to the person. Read the return value and the `HANDOFF.md` the run committed, and form a recommendation for each item it reports. Where you hold that recommendation with high confidence, act on it: apply it — including an edit to `spec.md` where that is the remedy — commit it, append what you did and what the confidence rested on to `<featureDir>/RESOLUTIONS.md`, and restart the run with the arguments the handoff names. Then tell the person what you decided, as work done and not as a question. Take an item to a person only where one of three things is true: you do not hold a recommendation with high confidence; the item has come back after its resolution was applied once; or the only resolution you can see is a move this skill forbids outright. An item that goes to a person goes with your recommendation and what is missing from it, never as a bare finding.**

Ground, 2026-09-22: one run stopped at analyze on three findings whose only remedy was a change to the spec, and the operator resolved all three by taking the session's own recommendation unchanged — a person relaying an answer the session already had. **The default this skill shipped until then was to relay every `needs-human` return to the person, and it lost to a rule this skill was already built on.** The owner's rule of 2026-09-18 is that a run never hands back work it could have done itself; every stop inside the loop is shaped to satisfy it — the forced convergence round, the bounded wall repairs, the reconcile behind a failed append — and the return value was the one place it stopped applying, because nothing said it bound the session that launched the run. It does now. **This does not move a single exit in `workflow.mjs`**: what the script stops on is unchanged, and what changed is who reads the stop first.

**High confidence, operationally: it is the recommendation you would hand the person expecting them to take it unchanged.** One answer, not options, and no hedge. If you would offer an alternative, or a caveat that could change the choice, that is not high confidence — the item goes to the person, with the recommendation and with what is missing from it. What makes confidence high is the repository's own text: the spec, the constitution, code, schema or configuration that existed before the feature, and the evidence the handoff quotes. **The run's own output can corroborate and can never be the whole of it** — `plan.md`, `tasks.md`, `data-model.md`, the contracts and the migrations were written *from* the spec by the run that just stopped, so resolving a stop by making the spec agree with them is the run rewriting the document its own gates are judged against. On a business value — a bound, rate, limit, period, threshold or name — one that nothing in the repository states or implies is not high confidence however obvious it looks from the code; one the spec already carries as its working value is, and that is what the observed case was.

**One attempt per item, and no retry of a retry.** This is the forced convergence round's rule one level out — a finding is forced at most once, and a survivor goes to a person with the record that the loop tried. Resolve an item once; if the restarted run stops on the same item again, that is tried-and-failed and it goes to the person with what was applied and why it did not take. `RESOLUTIONS.md` is what makes that test answerable by a session that was not the one which applied it, which is why the trace is a file and not a memory.

**What it does not license.** Every prohibition this skill puts on its own agents binds the session identically, and none of them becomes permissible because a person would have had to decide it. No gate is weakened, reordered or removed; no test skipped, quarantined or deleted; no suppression, exclusion, baseline entry, traceability waiver row or ignore comment; no lowered threshold or coverage figure; no edit to the wall script, the build file or any gate configuration; no force flag; **no commit on the base branch**; and nothing that resolves somebody else's state — an uncommitted tree preflight refused on, or a merge conflict between the base branch and the feature's committed work. Those last two are a person's because acting on them destroys work that is not the run's, which is the same reason preflight refuses rather than guesses. All of these stay escalations however good a recommendation you could write for them.

**Why the session may edit `spec.md` when no agent of the run may.** Position, not a loophole, and the ban inside the run is unchanged: an agent inside the loop is one the spec is the oracle for, and an artifact the run may rewrite cannot refute the run. The session is outside a stopped run, reading its whole report against the repository, and its edit is followed by a **restart at the stage the handoff names**, so every gate the edit touches runs again over it. The restart is the safety; an edit applied without one has none of it. **Until 2026-09-24 that was false for one stage**: a restart `from: "review-plan"` ran no review and went to tasks, so the seven review-plan stops restarted that way, 2026-09-21..23, reached tasks with no reviewer reading what had been applied; the script now runs the review on that start (run ledger, sweep 2).

**The trace is `<featureDir>/RESOLUTIONS.md`, appended to and never rewritten** — one dated section per stop, naming the stage, the reason the run gave and the run id from the Workflow tool result (the handoff cannot name it; 2026-09-24), and per item: the item as the handoff stated it, the recommendation, what the confidence rested on, and the commit that holds it; or, where it went to a person, that fact and what was missing. A file rather than a section of `HANDOFF.md` because the script overwrites that file at the next exit by design, and the one-attempt test has to be answerable by a session reading a *fresh* handoff without going through its git history; not commit messages alone, because a message carries the change and not the item it closed. A run that stopped before a base branch or a feature directory was resolved, or at preflight before it left the base branch, wrote no handoff and gets no `RESOLUTIONS.md` either — the report is the return value, for the script's own reason that it does not commit to the trunk.

(Check: on a feature the run has stopped on, `<featureDir>/RESOLUTIONS.md` exists and its newest section names the same stage as the current `HANDOFF.md` and a run id; every item in it is either applied, with a commit sha and what the confidence rested on, or marked taken to a person with the recommendation and what was missing from it; and the session's closing message to the person states decisions taken rather than asking about them. ## What this skill does not do

**It does not specify, clarify or write a spec**: that is the domain expert's, with stock spec-kit and the spec handoff, and the technical expert's for the handoff's Technical questions, before the run starts — a repository whose feature has no `spec.md`, or whose spec still holds a clarification marker, is refused at preflight rather than written by an agent. It does make the feature branch when there is none — on a start at preflight, and since 2026-09-25 on a later start on the base branch — and merges the base into it, which are the two git operations it performs; it never rebases, never force-pushes and never commits on the base branch. It does not read the handoff file back: a run that restarts does not know one was written, and nothing in the script reconciles `HANDOFF.md` with the state of the feature — the file is a report for whoever resolves the stop, which is the launching session and then a person, and a stale one is stale until the next exit overwrites it. Nor does the script write, read or enforce `RESOLUTIONS.md`: that file is the session's, and no gate in this repo reaches it. It does not install spec-kit or its skills; preflight fails when `speckit-plan` through `speckit-converge` are missing under `.claude/skills/`. It does not choose the definition of done: the project's `CLAUDE.md` names the command, or `args.wall` does. It does not merge unless `mergeInto` says where, and it never opens a pull request. It runs its stages in sequence — a feature's artifacts are one dependency chain and nothing in it is independent enough to fan out. It is Claude Code only: the Workflow tool, the skill-directory substitution and the per-agent model and effort are that client's, and the portable part — the stage prompts and the loop — is readable in `workflow.mjs` for anyone porting it. It does not record what it cost or which of its mechanisms fired: the Workflow journal does, under `~/.claude/projects/`, and that journal is machine-local, is in no repository, and is erased when that directory is cleared — so a run whose numbers matter is read back before then, and the status line below is what a reading is written down as. It removes the one gate the rest of this set assumes a person reads — the plan, the last cheap moment a wrong decision is caught — and puts the review-plan refutation there instead; a person who wants that read runs with `until: "review-plan"`, reads the plan, and continues with `from: "tasks"`.
