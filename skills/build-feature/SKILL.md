# Build a feature — the spec-kit cycle from a finished spec, with no human gate

**Two skills run this skill's script.** `plan-feature` ships it as its own `workflow.mjs` and runs preflight to analyze and ends by handing every question the spec leaves to the domain expert in `QUESTIONS.md`; this skill runs implement, converge and finish on a feature that `plan-feature` left with no open question, and closes out an already-implemented feature the same way, since implement skips every phase already done. The process is three loops over stock spec-kit commands: the domain expert's `/speckit-specify` and `/speckit-clarify` on the base branch; `plan-feature` and the domain expert's `/speckit-clarify` over its questions, repeated until no question is open; then this skill. This file and [reference.md](reference.md) are the reference for the whole script, both halves: this file holds what the session needs to start the script and handle its return, and `reference.md` holds how each stage works and where it stops; read it when a return or a handoff needs that mechanism.

The code is written by LLM agents and no human reads it line by line, so the human gates spec-kit puts between its commands are replaced: one deterministic script, one fresh subagent per stage, a refutation review where each gate was, and a converge loop that ends at a severity floor, which by default tolerates no finding. **The specification is not automated.** A domain expert writes `spec.md` with stock `/speckit-specify` and `/speckit-clarify`; the script starts at `plan` and never writes that file.

## Run the workflow; orchestrate nothing yourself

**Call the Workflow tool with this skill's script from `implement`, from the base branch or the build branch, once `plan-feature` has ended with `status: "done"` or every question in `QUESTIONS.md` is left open, and run no spec-kit command from your own context.**

```
Workflow({
  scriptPath: "${CLAUDE_SKILL_DIR}/workflow.mjs",
  args: { from: "implement", featureDir: "specs/004-product-gl-config",
          wall: "node backend/scripts/wall.mjs" }
})
```

`wall` is the definition-of-done command the project's root `CLAUDE.md` names; a start after preflight must pass it. **A start at implement or later refuses while `<featureDir>/QUESTIONS.md` holds an open question, or cannot be read**: a `CRITICAL` or `HIGH` question the spec has not answered, or a `MEDIUM` or `LOW` one no person has left open. A file whose every question reads `yes — <who>` in its `Left open` column does not stop it. The refusal names `plan-feature` with `from: "review-plan"` as the next step once the domain expert has answered. The script with no `from` and no `until` runs every stage in one call and stops after analyze whenever a question is open; neither skill starts it that way.

Do not run `/speckit-plan` or any other spec-kit command yourself and judge the result: the context that wrote an artifact must not be the one that approves it. Do not use `specify workflow run speckit` either: its gates need a terminal, its effort cannot be set per step, and its command steps capture no output, so it cannot loop on what converge reports.

**Service projects work trunk-based on the base branch: everyone commits to `dev`, and the long-lived feature branch does not exist.** Preflight discovers what the run is for and puts the repository where the stage belongs; nothing is required on a first planning run.

- **Planning runs on the base branch; the build runs on a branch that lives only for the build, `build/<NNN>-<name>`** (or `args.branch`), which preflight makes from the up-to-date base, or resumes, only once every preflight check has passed, and which finish lands on the base by fast-forward and deletes. How each start brings the base up to date, retries a push, records the spec the plan review read, merges the base into the build branch and lands it is in [reference.md](reference.md#branches).
- **A feature's spec is fixed once its build branch exists.** A later change to what the feature does is specified as a new feature whose spec states the change it makes to this one. Where the base's `spec.md` differs from the build branch's, nothing is merged or landed and the run stops; the stop tells the technical expert to revert the commit that changed it on the base with `git revert` and push — never a history rewrite — and the domain expert to specify the change as a new feature, after which the build restarts where it stopped.
- **Feature directory:** `args.featureDir`, which preflight is given as the feature and never searches past: a preflight return naming another directory, or none, is asked once more and then stops the run. Without it, the checked-out branch name (`build/<NNN>-<name>` → `specs/<NNN>-<name>`), else — a planning start — the one directory under `specs/` with a written `spec.md` and no `plan.md`, or — a build start — the one directory whose `tasks.md` on the base holds an open task; `.specify/feature.json` last, never overriding, because it is machine-local and names whichever feature this checkout last specified. Two candidates or none is a `needs-human` exit listing them, never a pick; the base holds several planned features, so every restart passes `featureDir`, and so does a close-out of a feature whose tasks are all ticked.
- With `push: false` the run contacts no remote: nothing is fetched, pulled or pushed, and finish fast-forwards the local base only.

The script path is this skill's own directory, substituted by Claude Code when the skill loads. A workflow starts only from a script the session may read, so a user-level install under `~/.claude/skills/` needs that directory added first — `/add-dir` with the same path, or a `Read` allow rule; a project-level install under `.claude/skills/` needs nothing. From a terminal: `claude -p "/build-feature" --permission-mode bypassPermissions`; the dispatching session can be the cheapest model, and it stays open until the workflow ends (idle ceiling `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`).

**The base branch is discovered, not assumed:** `args.baseBranch`; else one line in the repository root's `CLAUDE.md` of exactly the form `` Base branch: `dev` `` (branch name in backticks, the line unindented and alone, once); else `origin/HEAD` naming a local branch; else the one local branch among `main`, `master`, `develop` and `dev`, where exactly one exists; else the run stops at preflight before anything is checked out, merged or written, and names the fix — add that line, or pass `baseBranch`.

**A service works on `dev`: a base branch of `main` or `master`, from any of those sources, stops the run at preflight** before anything is checked out, merged or written, and names the fix — make `dev`, commit `` Base branch: `dev` `` on it, make it the forge's default branch. `main` takes pull requests from `dev` only, merged by a person when `dev` is stable, so no feature is planned, built or landed against it; `mergeInto: "main"` or `"master"` throws before the first agent starts.

How preflight reads each source and where it stops are in [reference.md](reference.md#base-branch-discovery). Each of those stops names its fix, as does the stop of a later start whose input artifacts are missing ([reference.md](reference.md#inputs-a-later-start-checks)).

Optional `args`, all with a default: `featureDir`, `branch` (the build branch's name), `baseBranch`, `wall` (read from the project's `CLAUDE.md` on a full run), `planGuidance` and `tasksGuidance` (passed to `/speckit-plan` and `/speckit-tasks`), `push` (default true), `mergeInto` (accepted for compatibility; anything but the base branch throws), `maxReviewRounds` 3, `maxAnalyzeRounds` 3 (ordinary fix rounds before the cap fix and the final review, in [reference.md](reference.md#a-gate-is-a-fresh-context-refutation-not-a-human)), `maxConvergeRounds` 6, `maxWallAttempts` 3, `severityFloor` (default `NONE`), `tiers`. To restart, pass `from` (`preflight`, `plan`, `review-plan`, `tasks`, `analyze`, `implement`, `converge`, `finish`) and `wall`; `until` bounds a run the same way, and an unknown stage name throws before the first agent starts. `from: "review-plan"` reviews the plan already on the base branch against the spec as it stands, without regenerating it; `from: "plan"` regenerates the plan and discards every review fix. Discovery, bringing the base up to date, the build branch's sync and `.specify/feature.json` run on every entry, restarts included. A run with no `from` and no `until` plans on the base branch, pushes, and then makes the build branch before `implement`. An interrupted run resumes with `resumeFromRunId`, which replays every finished agent from its journal.

Under the default `severityFloor`, `NONE`, a run usually ends converge at its round cap or at `needs-human`. A round-cap run goes on to finish, where the wall decides, and reports the last assessment's findings open under `converge.ended: "round-cap"`: the wall plus the reported findings say the feature is done. The floor's legal values are in [reference.md](reference.md#analyze-goes-back-to-the-artifact-it-names-converge-goes-back-to-implement).

## The spec is fixed input, and no stage of this run edits it

**`<featureDir>/spec.md` is the fixed input: every stage reads it, no stage — no review fix, remediation, implement pass, repair or forced convergence task — writes it, and a finding a planning stage can close only by a change to the spec is a question for the domain expert, with a recommended answer. Nobody but the domain expert writes the spec: not the run, and not the session that launched it.** An artifact the run may rewrite cannot refute the run, so do not *align the spec* with what the run decided or built.

- **Each question carries a severity: what a different answer would undo.** `CRITICAL` or `HIGH` where it would change what the feature does — a requirement's behaviour, the data model, a contract, a state or transition, an error case, a security, money or compliance rule; `MEDIUM` or `LOW` where it changes a local detail — a message, a label, a default, a documented value — that one later task can change. Each also carries what a different answer would change, in one sentence. After analyze, a run holding an open question returns `needs-human` with every question at once, committing `<featureDir>/QUESTIONS.md` beside `HANDOFF.md`.
- **Only a person leaves a question open, and only a `MEDIUM` or `LOW` one.** The technical expert, or the domain expert through them, says the build may start on the recommended answers; the session records it as `yes — <who>` in the question's `Left open` cell, commits that file alone and pushes. The domain expert can still answer it later or never. The session never leaves one open on its own judgment. A `CRITICAL` or `HIGH` question reads `cannot be left open`.
- **`QUESTIONS.md` and the top of `HANDOFF.md` show the questions as one table** — question, recommended answer, what a different answer would change, severity, left open — then the numbers the build waits for. A later planning run carries the questions left open into the file it rewrites, and its restart review drops one the spec now answers.

**After the domain expert has answered into the spec, `plan-feature` restarts at `from: "review-plan"`, whatever stage stopped, and never at `plan` unless a person asks for a new plan.** How the stages collect questions, what that restart reviews, which exits return `restartFrom` and with which stage, and how `tasks.md` is updated in place over work already done are in [reference.md](reference.md#spec-questions-and-the-restart-after-an-answer).

## Each stage runs on the tier it earns

**Take the model and effort of every stage from the `TIERS` table in `workflow.mjs`; every row is Opus or Sonnet at low, medium, high or xhigh effort. Change a row for one run with `args.tiers`, never by editing the table.** The models are the aliases `opus` and `sonnet`, not pinned ids, because `agent()`'s `model` takes aliases; they resolve to Opus 5.5 and Sonnet 5.5. A row on any other model, or on `max`, fails the run before its first agent starts. The table of stages with the reason for each row is in [reference.md](reference.md#the-tier-of-each-stage).

## A needs-human exit leaves a file behind

**What stops the script.** Each stop goes to the launching session first; only the three classes in the resolution rule below reach a person. Every stop carries what was attempted and how often. A converge loop at its round cap is not a stop. Preflight's exits commit nothing, and the return value is the report; preflight makes no branch. Every stop is listed in [reference.md](reference.md#what-stops-the-script).

**Every `needs-human` exit after preflight writes `HANDOFF.md` into the feature directory, commits it where the run stands — the base branch during planning, the build branch during the build — and pushes it when `push` is true, before it returns** — with `QUESTIONS.md` beside it when the run holds questions for the domain expert. A `done` return whose questions left open changed rewrites `QUESTIONS.md` alone. The file starts with the questions table when the run holds questions, then says that the run stopped and who reads it first, then carries the stage, the reason, the full findings item by item, the branch, the round counts, the stages run, the definition-of-done command, the severity floor, the date, the arguments that restart the run, and where the run journal is kept. **It names no journal path:** the script cannot see its own run id; the run id is on the Workflow tool result, and the session records it in `RESOLUTIONS.md`. The document is rendered in `workflow.mjs` and handed finished to one Sonnet agent, with one placeholder, the date, so the agent cannot paraphrase or drop a finding. The commit is by pathspec, those files only, because the tree may hold the run's failing work.

**A failed handoff never costs the run its verdict:** the full payload stays on the return value, with `handoff.written: false` and the reason in `handoff.note`. **An exit before a base branch or a feature directory is resolved, every preflight exit, an exit on a detached HEAD, a build stop before the run is on its build branch, and an exit whose planning commits could not be pushed write nothing** and say so on the return. A stop at `finish` gets the same file, on the build branch that did not land, on a return that keeps its own shape.

## A needs-human return is the session's to resolve, not to relay

**When the workflow returns `status: "needs-human"`, do not hand it to the person. Read the return value and `HANDOFF.md`, and form a recommendation for each item. Where you hold it with high confidence, act on it: apply it — never as an edit to `spec.md`, which is the domain expert's alone — commit it, append what you did and what the confidence rested on to `<featureDir>/RESOLUTIONS.md`, and restart the run with the arguments the handoff names. Then tell the person what you decided, as work done. Take an item to a person only where you do not hold a high-confidence recommendation, where the item came back after its resolution was applied once, or where the only resolution is a move this skill forbids. An item that goes to a person goes with your recommendation and what is missing from it.**

**High confidence: the recommendation you would hand the person expecting them to take it unchanged.** One answer, no hedge; an alternative or a caveat that could change the choice means it goes to the person. It rests on the repository's own text — the spec, the constitution, code, schema or configuration that existed before the feature, and the evidence the handoff quotes. **The run's own output can corroborate and never be the whole of it**: `plan.md`, `tasks.md`, the data model, contracts and migrations were written from the spec by the run that stopped. A business value — a bound, rate, limit, period, threshold or name — that nothing in the repository states or implies is not high confidence; one the spec already carries as its working value is.

**One attempt per item, no retry of a retry.** If the restarted run stops on the same item, it goes to the person with what was applied and why it did not take.

**What it does not license.** Every prohibition on the run's agents binds the session: no gate weakened, reordered or removed; no test skipped, quarantined or deleted; no suppression, exclusion, baseline entry, waiver row or ignore comment; no lowered threshold or coverage figure; no edit to the wall script, the build file or any gate configuration; no force flag; **no commit on the base branch outside the feature directory, and none to the feature's `spec.md` or plan while its build branch exists** — a planning stop is resolved on the base branch, a build stop on the build branch; and nothing that resolves somebody else's state — an uncommitted tree preflight refused on, or a conflict between the base and the feature's work.

**A change to the spec is the domain expert's, never the session's.** The session answers every technical question that leaves the spec as it is. When the return carries `questions`, show the person the questions table first, ask whether the `MEDIUM` and `LOW` ones may be left open as `plan-feature` words it, send the domain expert the one line in `clarifyCommand` — the same line is in `QUESTIONS.md` — and add nothing to the spec; `/speckit-clarify` shows each question with its recommendation, and skips one the spec already answers. The restart after their answer is `plan-feature` with `from: "review-plan"`.

**The trace is `<featureDir>/RESOLUTIONS.md`, appended to and never rewritten** — one dated section per stop, naming the stage, the reason and the run id, and per item: the item as the handoff stated it, the recommendation, what the confidence rested on, and the commit; or, where it went to a person, that fact and what was missing. It is a file because the script overwrites `HANDOFF.md` at the next exit, and the one-attempt test must be answerable by a later session. A run that wrote no handoff gets no `RESOLUTIONS.md` either.

## What this skill does not do

**It does not specify, clarify or write a spec**: that is the domain expert's, before the run and again over `QUESTIONS.md`; a feature with no `spec.md`, or with a clarification marker left, is refused at preflight. Its only git operations are bringing the base up to date by fast-forward, planning commits on the base inside the feature directory and what the plan step writes outside it, `git pull --rebase` of the run's own unpushed commits before a push, making or resuming the build branch and merging the base into it, and landing the build on the base by fast-forward; it never rebases shared history, never force-pushes and never writes another feature's spec. It reads `QUESTIONS.md` only for its questions, their severity and whether each is left open; it never reads `HANDOFF.md` back; it does not write, read or enforce `RESOLUTIONS.md`. It does not install spec-kit; preflight fails when `speckit-plan` through `speckit-converge` are missing under `.claude/skills/`, and, on every start, when the traceability gate `/init-pipeline` installs or its self-test is missing or not listed in `scripts/wall-checks.txt`. It does not choose the definition of done. It lands every finished build on the base branch and never opens a pull request; merging `dev` into `main` is a person's. It runs stages in sequence. It is Claude Code only; the stage prompts and the loop in `workflow.mjs` are the portable part. It does not record its cost: the Workflow journal does, machine-local under `~/.claude/projects/`. It replaces the human plan review with the review-plan refutation; a person who wants to read the plan runs with `until: "review-plan"`, reads it, and continues with `from: "tasks"`.
