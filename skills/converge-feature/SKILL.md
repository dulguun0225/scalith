# Converge a feature — the loop alone, against work that already exists

**Premise, shared with every skill in this set:** the code is written by LLM agents and no human reads it line by line. The consequence for a feature that is already implemented is that *is it done* is a question `/speckit-converge` answers by reading the code against the spec, plan and tasks — and on the one run that measured it (2026-09-18) the answer kept changing: converge has no fixed point, each pass finds what the previous implement did not, and the loop ends at a written severity floor — `NONE`, tolerating nothing, unless the caller names another — or it does not end and reports what is open at its round cap. This skill is a named entry point to that loop. It runs `build-feature`'s script from its converge stage, and nothing else.

## Call build-feature's script; write no loop

**Call the Workflow tool with `build-feature`'s `workflow.mjs`, reached as a sibling of this skill's directory, with `from: "converge"` and `until: "finish"`, and run no `speckit-*` skill from your own context.**

```
Workflow({
  scriptPath: "${CLAUDE_SKILL_DIR}/../build-feature/workflow.mjs",
  args: { wall: "node backend/scripts/wall.mjs",
          severityFloor: "NONE",
          from: "converge", until: "finish" }
})
```

`build-feature` installed beside this skill is a precondition, not a suggestion: this skill ships no script, because one loop exists and it is that one. A workflow starts only from a script the session may read, so a user-level install under `~/.claude/skills/` needs that directory added first — `/add-dir` with the same path, or a `Read` allow rule — where a project-level install under `.claude/skills/` needs nothing; the same "cannot read" refusal with `build-feature` sitting beside this skill on disk means that missing permission and not a missing install. A missing sibling fails loudly at the same Workflow call — the tool refuses a `scriptPath` it cannot read — and the fix for that case is `npx skills add dulguun0225/scalith`, which installs both. **Run it on the feature's own branch, checked out.** Since 2026-09-21 `build-feature`'s preflight discovers the feature on every entry, this one included — from `args.featureDir`, else the branch name, else the one specified-but-unplanned directory under `specs/`, and only last from `.specify/feature.json`, which is git-ignored machine-local state and may name another feature entirely — so on the feature branch neither `featureDir` nor `branch` has to be passed. Pass `featureDir: "specs/<nnn>-<feature>"` and `branch: "<feature-branch>"` to override that discovery, which is what a feature the current checkout is not on needs. That same preflight points `.specify/feature.json` at the feature it resolved, because spec-kit resolves the feature from that file and never from the branch name, and it merges the base branch into the feature branch before the loop starts, so the close-out is assessed against the spec as it stands. Started on a feature branch, it creates no branch. **Started on the base branch, pass `featureDir`:** discovery there answers only with the one specified-but-unplanned directory under `specs/`, never a feature already planned or implemented, so without it the run resolves that other feature and stops on its missing `plan.md`, saying so (2026-09-25). **Started on the base branch — a feature implemented on the trunk — preflight refuses a dirty tree, then makes the feature branch at the base branch's HEAD, under the name a full run would make, checks it out, and the loop runs and commits there; no stage commits on the base branch** (`build-feature`, owner's decision 2026-09-25). A feature branch of that name that already holds work the base lacks stops the run at preflight rather than being picked, where the base branch holds `plan.md` or `tasks.md` too; where it holds neither, the feature's work is on that branch, and preflight checks it out and merges the base in. `plan.md` and `tasks.md` are checked on the branch the run would work on before any branch is made, and a missing one stops the run on the base branch with no branch made and nothing committed (2026-09-25). The return value names the branch and carries `createdBranch`, and a `HANDOFF.md` is committed on it; only a preflight exit taken before the branch is made — a dirty tree or a missing `plan.md` or `tasks.md` among them — leaves none. **Which branch is the base is discovered, not assumed** (`build-feature`, owner's decision 2026-09-25): `baseBranch` where passed, else the line `` Base branch: `<branch>` `` in the repository root's `CLAUDE.md` as committed on the branch the run starts on (later that day), else `origin/HEAD`, else the one local `main`, `master`, `develop` or `dev`, and a run where none answers, or whose line cannot be read or names no local branch, stops at preflight having written nothing — so in a clone with no `origin/HEAD` and both `main` and `dev`, which is each of the three service repositories as read that day, the line is what lets this skill's example run without `baseBranch`. The return value carries `baseBranch` and where it came from. The loop's commits then reach the base branch only through `mergeInto`, which fast-forwards it, or a person's merge. Until that day such a run stayed on the trunk and its converge and implement agents committed there. **`args.wall` is required on any start after preflight**, this one included: preflight is the stage that reads the definition-of-done command from the project's `CLAUDE.md`, and a run that skips it would hand every prompt the string `null` as the command — the script refuses to start without it (defect observed 2026-09-17, recorded in `build-feature`). A run interrupted mid-loop resumes with `resumeFromRunId`, which replays every finished agent from its journal and picks up at the round it was in. **`args.severityFloor` is where the loop stops, and this skill is the place a user sets it: one of `NONE`, `LOW`, `MEDIUM`, `HIGH`, defaulting to `NONE` — the loop ends on the first round whose findings hold nothing above it, and `NONE` ranks below every graded severity, so the default tolerates no finding at all and the loop ends only on a round that appends nothing and grades nothing, or at `maxConvergeRounds`. Raise it to `LOW` or `MEDIUM` to close a feature out on the gaps a person would notice and leave the wording and naming findings. `CRITICAL` is on `/speckit-converge`'s grading scale but is not a legal floor, because a floor there tolerates a constitution MUST violation and ends the loop after one round; it throws, as does any other value, before the first agent starts.** Expect a run at the default to end at the round cap with its open findings reported; that is the intended behaviour and not a failure of the loop — the wall at finish is still the gate. Where converge calls a round converged while still grading a gap the loop no longer stops: it appends that gap itself as a forced convergence round, implements it and re-assesses, because a floor that declines converge's non-actionability judgment owes the work that judgment withheld (`build-feature`, 2026-09-18). A forced task is closed by the fix alone — there is no written-reason route, and a fix counts as blocked only where a numbered requirement or constitution article forbids it, it needs a system that does not exist, or its only remedy is an edit to `spec.md`, which no stage of the loop makes because the spec is its author's (`build-feature`, 2026-09-20 and 2026-09-21); a blocked task stays unticked and the run exits `needs-human` with the blockers named and everything else fixed. Only a gap that survives its own forced round — appended, implemented, wall green, and reported again — is `needs-human`, and the handoff says the loop already tried. **One gap is never forced: an item `spec.md` itself defers or puts outside the feature's scope** — the assessment returns it with the spec text quoted, a parse-only agent checks that the quotation is in `spec.md`, and the loop reports it under `converge.deferred` and does not count it against the floor — a quotation the check does not find exempts nothing (`build-feature`, 2026-09-24, after `wf_e4af9888-80a` forced a requirement the owner's clarification had deferred). A deferral written anywhere but `spec.md` — `plan.md`, `tasks.md`, a `GATES.md` row, a waiver row — exempts nothing, because the run wrote it. A question only the spec's author can answer stops the run, and its restart after the spec is edited is `from: "review-plan"`, not `from: "converge"`, since the plan and tasks were derived from the old text. On a feature this skill closes out, that restart does not regenerate `tasks.md`: its tasks stage finds ticked tasks and updates the file in place — ticked work stays ticked, forced convergence phases included; a task whose requirement the spec edit changed is unticked with the reason in its line; a task no longer needed is struck through as `(removed: …)`, never deleted; new work gets new unticked tasks — a parse-only reader certifies that no ticked task was lost, and implement runs only what is open (`build-feature`, owner's decision 2026-09-25; no run has taken it). A forced append that fails to write `tasks.md` is reconciled against git and retried once before it escalates (`build-feature`, 2026-09-19), so that exit too means the loop tried and says what it found in the file. Every other `build-feature` argument applies unchanged, with its default: `maxConvergeRounds` 6, `maxWallAttempts` 3, `push` **default true** — so the example above has finish push the feature branch, the one preflight made included; pass `push: false` where that is not wanted — `mergeInto` **default none**, so nothing is merged unless a branch is named, and `tiers`. The loop's stop rule, its tier table and its exits are `build-feature`'s and are stated there, not here.

The default an agent reaches for is `/loop`: *Run /speckit-converge then /speckit-implement until converge appends nothing*, retyped into the session. Rejected 2026-09-18 against the `001-product-hierarchy` run this skill is written from, on three grounds. The stop condition is re-judged by feel each tick rather than written down — that run took five passes, and the fifth appended nothing only because the operator had stopped applying findings below the floor; the script writes the rule (stop when the assessment grades nothing above `args.severityFloor`, which by default is `NONE` and tolerates nothing, so the operator's judgment is not what ends the loop) and logs which round's assessment ended the loop. Each tick re-enters the main context, so nothing is journalled or resumable and the subagents it spawns inherit the session's model rather than the stage's tier — converge on Opus medium, implement on Opus medium, phases on Opus low, every row checked against the roster before the first agent starts. And it is a sentence retyped per feature and per project, which is the shape this whole skill set exists to replace.

## A needs-human return is yours to resolve, not to relay

**When the run returns `status: "needs-human"`, read the return and the `HANDOFF.md` it committed, form a recommendation per item, and act on every one you hold with high confidence — apply it, an edit to `spec.md` included where that is the remedy, commit it, append what you did and what the confidence rested on to `<featureDir>/RESOLUTIONS.md`, restart the run with the arguments the handoff names, and report to the person what you decided rather than asking. Take an item to a person only where you do not hold a recommendation with high confidence, where it comes back after its resolution was applied once, or where the only resolution is a move the skill forbids outright — and it goes with your recommendation and what is missing from it, never as a bare finding.** High confidence is the recommendation you would hand the person expecting them to take it unchanged: one answer, no hedge, no alternative that could change the choice. It rests on the repository's own text — the spec, the constitution, the code, the evidence the handoff quotes — and the run's own `plan.md` and `tasks.md` can corroborate but never be the whole of it, because they were written from the spec by the run that just stopped. A business value nothing in the repository states or implies is not high confidence; one the spec already carries as its working value is. The prohibitions bind you exactly as they bind the script's agents: no gate weakened, no test skipped or deleted, no suppression, baseline or waiver row, no force flag, no commit on the base branch, and no resolving somebody else's uncommitted tree or merge conflict — those stay escalations whatever recommendation you could write.

`build-feature` owns this rule and carries its ground, its rejected default and the reason the session may edit a file its agents may not; this paragraph is the index beside it, and the duplication is deliberate and is the only one in these two skills. The reason is loading, not installing: `build-feature` must be on the same disk for this skill to run at all, but a session that invokes `/converge-feature` alone never loads that skill's body, and a rule that governs what this session does when its own call returns has to be in the text that call was made from. Everything else about the loop — its stop rule, its tier table, its exits — stays stated there and not here.

(Check: on a feature this skill stopped on, `<featureDir>/RESOLUTIONS.md` exists, its newest section names the stage of the current `HANDOFF.md`, and every item in it is applied with a commit and what the confidence rested on, or marked taken to a person with the recommendation and what was missing; the closing message states decisions rather than questions. Nothing mechanised — the session runs outside `workflow.mjs` — *convention*, 2026-09-22.)

## What this skill does not do

It does not plan, review or analyze: a feature that lacks `plan.md` or `tasks.md` is refused at the loop's preflight, which names the missing files and the `from` that writes them (`build-feature`, 2026-09-24), and on the base branch makes no branch first (2026-09-25); one whose tasks are largely unchecked is `build-feature`'s with `from: "implement"`, and running this skill on it makes converge append the whole feature as one phase. It writes no spec either, and neither does the script behind it — a feature directory with no `spec.md` is its domain expert's to fill with `/speckit-specify`, and the loop's own preflight discovery refuses without one (`build-feature`, 2026-09-21). It does not decide how the loop stops or what a round may cost — `build-feature` does, in its script and its tier table, and a change to either is made there once rather than here; `severityFloor` is an argument that skill defines and this one passes, not a rule this one owns. It does not run without `build-feature` on the same disk. **It does not record what a run cost or which of its mechanisms fired** — the Workflow journal does, machine-local under `~/.claude/projects/` and erased with that directory, which is why a run whose numbers matter is read back before then. The cost is no longer absent: over forty-nine real runs of this loop's script, 2026-09-17..24, converge was the second-dearest stage after implement, at fifty-five agents and a mean near 150,000 subagent tokens each, and the four runs of 2026-09-20 that took the severity floor to the round cap spent between 1.70M and 2.47M tokens and 46 to 60 minutes apiece (re-read with `npm run runs` in the repository these skills distribute from; every figure here carries its date because it moves).
