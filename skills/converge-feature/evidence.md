# Converge a feature — evidence

For a human deciding whether to trust the directive text. Every claim below is *convention* — a decision recorded with its date and observed ground, no research pass and no refutation panel behind it.

## Call build-feature's script; write no loop

Ground, 2026-09-18: feature `001-product-hierarchy` of a spec-kit Java backend (the product-catalog repo, `main`, head `f2b5f1f`), fully implemented and wall-green, converged by hand — `/speckit-converge`, then `/speckit-implement` on the appended phase, then the wall, repeated. Five passes. Each pass found something the previous implement had not (a gate the plan named and the code lacked, a request limit not on the wire, a pattern not on the wire, wording), and the fifth appended nothing only because the operator had stopped applying findings graded LOW. The rule the operator arrived at by running it — stop when nothing converge reports is above LOW, not when converge appends nothing — became the stop rule in `build-feature`'s script, with the round cap raised from three to six and reaching it reported rather than escalated. *(The floor is still the only stop test, but `LOW` is no longer the default: see the last entry of this file.)* Before that change the script would have exited `needs-human` at round three of this run.

Why a second skill rather than a paragraph in `build-feature`: the loop is invoked at a different moment — after implement, against work that exists, often on a feature `build-feature` never touched — and a skill fires on the moment its description names. The alternative was `/loop` with a retyped sentence; rejected the same day on the three grounds the directive states: an unwritten stop condition re-judged each tick, no journal and no resume and no per-stage tier because every tick re-enters the main context, and a sentence that is per feature and per project. The `/loop` sentence on this run was `Run /speckit-converge then /speckit-implement …`, and the operator ended it by judgment.

**2026-09-18, two corrections from an adversarial review of `cc903d0`.** Ground: a reading of the commit that created this skill, against `build-feature`'s own text, the same day it was written. **Nothing was executed — no run has been made through this skill, and the review is a reading, not a measurement.** First, the directive diagnosed the wrong cause for the failure a reader will actually hit. `build-feature` states that the Workflow tool accepts a `scriptPath` only from a directory the session may read, so a user-level install under `~/.claude/skills/` needs `/add-dir` or a `Read` allow rule first; this skill omitted that and told the reader an unreadable path means a missing sibling, with `npx skills add` as the fix — which does nothing for an install that is present but unreadable. The precondition is now stated here in the same terms, and the missing-sibling sentence is kept for its own case, which is real. Second, `push` and `mergeInto` were named without their defaults beside an example that runs on `branch: "main"`, so a reader following the example has finish push `main` directly with nothing on the page saying so. Both defaults are now inline, with the consequence for that example named. The stop rule this skill points at was corrected in the same pass and is stated in `build-feature`, not here: the severity floor is the loop's only stop test, a `converged` return carrying a finding above it ends the run `needs-human`, and the round cap is followed by one assess-only round whose findings are the ones the run carries.

Why no script of its own: `build-feature`'s `from` and `until` arguments already bound a run to any contiguous stage range, and a run starting after preflight already refuses to start without `args.wall` (the `state.wall = null` defect of 2026-09-17, recorded in that skill). Duplicating the loop would have created the second copy of a directive that this repo's write-once rule exists to prevent, and the two would have drifted at the first change to either. The sibling path `${CLAUDE_SKILL_DIR}/../build-feature/workflow.mjs` rests on the flat `skills/<name>/` layout both skills install into; a missing sibling fails at the Workflow call with the path it could not read, which is the loud failure the repo's rules require of a precondition.

**2026-09-18, the floor is chosen here.** *(Superseded in its default by the entry below.)* Ground: the owner asked that this skill be able to choose the severity floor, defaulting to `LOW`. The floor is `build-feature`'s argument and its check — `args.severityFloor`, validated against `HIGH`, `MEDIUM`, `LOW` (and now `NONE`) before the first agent starts, `CRITICAL` refused on a read of `/speckit-converge`'s Step 5, recorded in `build-feature`'s evidence file — and what changed here is where a reader is told about it: it is in the example call and stated as the one setting that moves where the loop stops, because this skill is the entry point invoked when a feature is already implemented and closing it out at `MEDIUM` rather than `LOW` is a per-feature call. Nothing was executed; the skill still has no run behind it.

**2026-09-18, the default floor is `NONE`.** Ground: the owner's decision, taken after being shown the counter-argument — the `001-product-hierarchy` run recorded at the head of this file, which is why `LOW` was chosen that morning — and reaffirmed. **Nothing was executed; no run has been made through this skill at any floor.** The rule and its check stay `build-feature`'s: `NONE` is a legal floor there, ranks below every graded severity, and is the default, so the loop tolerates no finding at all. What changed here is what a reader of this skill is told and what the example call shows — `severityFloor: "NONE"`, the legal set as `NONE`, `LOW`, `MEDIUM`, `HIGH`, and the frontmatter `description`, which said *until nothing converge reports is above LOW severity* and was false the moment the default moved. The description edit is the reason this entry names a cost: it invalidates any firing baseline, and this skill has never measured one.

The rejected alternative is the `LOW` default, and the ground it lost on is that a tolerated finding is a finding left open. The consequence for this skill's own use — closing out a feature that is already implemented — is the sharp one: a `converge-feature` run at the default will usually end at `maxConvergeRounds` with its open findings reported, or `needs-human` where converge reports converged while still grading a gap, rather than at a clean converge. A caller who wants the old behaviour passes `severityFloor: "LOW"`, which is why the floor is an argument and why this skill is where it is set.

## What this skill does not do

The scope boundary — converge to finish, nothing earlier — follows from what `/speckit-converge` does on a feature that is not implemented: it appends every unbuilt requirement as one phase, which is `/speckit-tasks` done badly. Cost is unmeasured: `build-feature`'s only end-to-end record put implement, converge and finish at about 2.2M subagent tokens for one converge round that reported converged; a run that takes several rounds at the floor now has one, dated 2026-09-22 at the foot of this file — three runs reached the six-round cap at floor `NONE` on 2026-09-20 for 2.25M to 2.47M subagent tokens and 49 to 60 minutes apiece.

**2026-09-18, a `converged` round with findings is no longer this skill's expected stopping place.** This skill's own text said to expect a run at the default floor to end at the round cap *or* `needs-human` where converge calls a round converged while still grading a gap. That second expectation is gone: `build-feature`'s loop now appends such a gap itself as a forced convergence round and implements it, and only a gap that survives its own forced round is a person's. Ground, dates and the rejected alternative are in `build-feature`'s evidence file — the loop, its stop rule and its exits are that skill's and are recorded once, there. The same applies to the reconcile-then-retry added behind a failed forced append on 2026-09-19: an exit this skill's text would otherwise have implied is a person's is the loop's, and it is recorded there. Unmeasured here as everywhere: no `converge-feature` run has taken the forced path, at any floor.

**2026-09-21, the arguments this skill passes changed under it, and one exit gained a third blocker.** Ground: the workflow change recorded in `build-feature`'s evidence file — features are specified by a domain expert with stock spec-kit, the script starts at `plan`, and no stage of it edits `spec.md`. **Nothing was executed here either; no run has been made through this skill at any floor.** Two consequences for this page. `featureDir` and `branch` are no longer things a caller must know: `build-feature`'s preflight discovers the feature on every entry, this skill's `from: "converge"` included, from `.specify/feature.json` or the branch name, so the example call is now the wall, the floor and the stage range, and the two arguments stay documented as the override a caller needs when the checkout is not on the feature. `args.wall` is unchanged and still required, for the reason it always was.
